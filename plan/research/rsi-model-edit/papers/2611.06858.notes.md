## 研究问题
coding agent 能否在给定存储预算、硬件、运行时和时间预算下，自主地把一个预训练 LLM 压缩成"仍然有用"的模型（压缩权重 + 可执行推理代码）？作者在摘要和引言里把这件事框定为递归自我改进（RSI）的一个具体、可测的组成部分：agent 改进后续 AI 系统所用模型的效率（p.1）。

## 方法细节
- **任务形式（Sec 2.1，p.3）**：给 agent 一个源 checkpoint p（只读）、存储上限 C、一张 GPU、固定的推理运行时（vLLM 0.32.0）、墙钟预算 T（8 小时），在离线容器里工作，容器里有 starter 推理代码、可检索的压缩论文、校准/恢复数据，以及一组用于本地测试的题目。候选 a=(W, I)：W 是压缩权重和元数据，I 是推理实现。搜索空间包括量化格式/舍入、分组件精度、剪枝、低秩、蒸馏；表示改变时 agent 必须自己写对应的推理算子。
- **存储约束**：S_pkg（磁盘包，含代码和 tokenizer）≤ C，S_res（推理时 GPU 常驻权重，含 scale、codebook、持久化的反量化副本）≤ C；KV cache 和临时 workspace 不计入（p.3）。
- **目标函数（Sec 2.3，p.4）**：在源模型自采样的续写上算交叉熵，超额交叉熵 Δ = H(q_a) − H(p)，其期望等于源到压缩模型的逐 token KL（式 3）。优化问题是在两个存储约束下最小化 Δ_s（式 4）。评估器返回 PPL 比 F = PPL(p)/PPL(q_a) = exp(−Δ)（式 5），搜索期奖励 r_s = 10·F_s（可执行且满足存储时），否则为 0（式 6）。时延不进奖励。
- **最终验证（Sec 2.4，p.4–5）**：冻结的产物在独立容器中运行，用不相交的验证上下文算 F_v，并测磁盘与常驻存储；GSM8K、HumanEval、TriviaQA 各 50 题的平均准确率须 ≥ 0.8×BF16（式 7，ρ=0.8，阈值对 agent 隐藏）；另有完整性审查（不能硬编码输出、不能操纵概率或计时）。最终分 R = F_v（全部通过时），否则为 0（式 8）。
- **效率测量**：报告 batch=1 的 decode 速度 TPS = 127/L（2048 token prompt，128 输出 token，预热后三轮取中位），**单独报告，不计分**（p.5–6）。不测 prefill/TTFT，不测吞吐。附录 E.4 报告了 device peak memory（Table A8，p.21）。
- **被压缩的模型（Sec 3.1，p.5）**：Nemotron-3.5 Super VL 120B-A12B（MoE）、Qwen3.5 122B-A10B（MoE），各设 32/48 GiB 两档；Qwen3.8 27B（dense），设 8/12 GiB 两档。全部是预训练好的开源 checkpoint。
- **做压缩的 agent**：Claude Sonnet 5.5、Claude Opus 5.5、GLM 5.3、Kimi K3.1 Pro、MiniMax M3.1 Flash、DeepSeek V4.1 Flash，全部通过 Claude Code 外壳运行（最大推理强度），每个 agent×任务只跑 1 次（p.5）。附录 E.1 对 GLM 和 DeepSeek 在 2 个任务上做了重复（Table A6，p.20）。
- **谁在压缩谁**：做决策、写代码的 agent 底座是闭源或 API 模型（Claude、GLM、Kimi 等）；被压缩的是 Nemotron/Qwen 的 checkpoint。**两者不是同一个模型，也不是同一个 checkpoint**。文中没有任何"agent 压缩自己"的实验，也没有"压缩后的模型接任下一轮 agent"的实验。唯一相关的表述在结论最后一句（p.12）：要把这一步推向 RSI，需要测试压缩后的模型是否还保有完成后续压缩任务的能力。这是作者明确列出的未来方向，本文没有做。
- **压缩形式与分工**：算法选择、组合、实现全部由 agent 决定，人类只提供任务、约束和评测。实际出现的方法有 GPTQ、Hadamard 旋转、trellis codes（QTIP 式）、混合精度/按敏感度分配比特、专家剪枝、MLP 宽度剪枝、低秩残差、KD 蒸馏等（Fig 4、Fig 9，p.7、p.10）。
- **多轮**：单个 run 内部有多次"构建→评估→修订"的迭代（v1、v2…），但这是对同一个源模型的搜索，不是递归（编辑者本身没有被替换）。
- **基线**：统一比特宽度的 GPTQ（group 128，128×2048 校准序列）；已发布的量化版本（Unsloth Dynamic GGUF、GSQ-RCO）（p.5）。

## 关键实验与数字
1. **通过率**：36 个提交中 29 个通过最终验证；宽松档 18/18 全部通过；严格档 6 个准确率不达标、1 个超时（Sec 3.2，p.6；Table 1，p.6；Table A3，p.18）。
2. **每个任务取 PPL 最低的 agent 产物**：相对 BF16 平均 PPL 上升 3.4%，下游准确率 77.33%，BF16 重测为 79.56%（摘要 p.1；Sec 3.2，p.7）。
3. **Table 1（p.6）代表性数字**：Qwen3.8 27B / 12 GiB 下 Sonnet 5.5 PPL 3.253、Acc 76.67%、TPS 16.7；BF16 为 3.221 / 74.00% / 61.4；已发布的 GSQ-RCO 为 3.334 / 66.00% / 74.6。Qwen3.8 / 8 GiB 下统一 GPTQ 为 PPL 7.480、Acc 4.67%（失败）。
4. **效率并没有变好**：几乎所有 agent 产物的 batch-1 decode TPS 都低于 BF16，例如 Nemotron 48 GiB 下 Opus 为 68.2，BF16 为 147.5；Kimi 在 Qwen3.5 48 GiB 下只有 7.8（Table 1，p.6）。作者明确说存储与质量上的改进本身不等于加速（p.11）。
5. **固定存储下的修订**：在 24 次包大小变化 ≤ 0.01 GiB 的修订中，有 21 次降低了 PPL（Sec 4.1，p.7；Fig 4，p.7）。例：Kimi 在严格档 Qwen3.5 上改 clipping 和 GPTQ damping，反馈 PPL 从 3.738 降到 3.132（p.7）。
6. **局部指标与整模型反馈不一致**：79 次匹配比较中，有 17 次局部排序被奖励反馈推翻，其中 8 次导致显式回滚（Kimi 5 次、DeepSeek 3 次）（Sec 4.2，p.8；Fig A2，p.21）。
7. **PPL 掩盖能力变化**：Opus 在 Qwen3.8 / 8 GiB 上的蒸馏版本中 PPL 持续改善，GSM8K 却从 88% 降到 72%（Sec 4.3，p.9；附录 C，p.17）。Sonnet 的 v3/v4/v5 PPL 分别为 3.2572、3.2531、3.2525，而 150 题中分别答对 111、104、115 题（p.11）。
8. **Bug 修复**：MiniMax 在 Nemotron 上发现专家索引 bug，修复后 PPL 相对 BF16 的增幅从约 11% 降到 4.5%（p.10）。
9. **重复性**：4 次重复运行全部通过，PPL 与原始运行相差在 0.81% 以内（Table A6，p.20）。
10. **停止行为**：17 个 run 在 agent 首次宣布完成后仍然修改了权重（附录 B，p.16；Fig A1，p.17）。
11. **API 成本**：最贵不等于最好；Sonnet 平均 PPL 排名最好，其次是 Opus（Fig 1b，p.2；p.7）。

## 作者自己声明的局限与 future work
- 结论（p.12）：要把这一步推向 RSI，需要测试压缩后的模型是否还能完成后续的压缩任务。这正是 self-compression/递归，作者把它列为下一步，本文未做。
- TPS 不计分，解包和反量化开销可能抵消内存流量的节省；存储与质量的改进不等于加速（Table 1 caption p.6；p.11）。
- 存储上限约束的是常驻权重，不是 GPU 总峰值内存（p.3）。
- 每个 agent×任务只跑 1 次（p.5），仅部分重复。
- 只看 likelihood 不足以验证模型；agent 往往检测到退化却保留了有问题的设计，或者没有让测试跟上最终产物（Sec 4.3，p.9–10）。
- 文中没有单独的 Limitations 章节，以上是散见于正文的说明。

## 方法问题与替代解释
- 【推断】奖励只用 PPL 比，准确率门槛对 agent 隐藏，于是 agent 被引导去优化 likelihood，自然会出现 PPL 改善而 GSM8K 下降。这更像奖励设计的产物，不一定反映 agent 能力的上限。
- 【推断】效率目标名义上是"推理效率"，实际只约束存储；多数产物 decode 比 BF16 慢（BF16 的 MoE 用两卡、压缩模型用一卡，对比口径并不完全对等）。所以"压缩=推理效率提升"在本文里并没有被证实。
- 【推断】每对 agent×任务 n=1，加上 50 题×3 的小评测集，单任务的 agent 排名噪声较大；Table A6 中 GLM 重复运行的平均准确率从 80.67 降到 68.67，说明准确率方差不小。
- 【猜测】agent 都运行在 Claude Code 外壳中，非 Claude 模型可能处于不利地位，排名的一部分可能来自外壳适配，而不是压缩能力本身。
- 【推断】被压缩的是 27B–122B 的开源模型，agent 是更强的前沿模型，这是"强模型压缩弱模型"的设置。agent 压缩自身时会面临不同的问题（例如压缩后编辑者自身能力下降），本文结论不能直接外推到那种情形。

## 与每个 core claim 的关系
- **C1（LLM 自主决定并执行对"自身"权重的压缩，目标是推理效率并保持能力）**：本文高度覆盖"LLM agent 自主决定并执行压缩"这一部分：agent 自选算法、自写代码、自做实验，目标是存储预算下保持行为，并有能力门槛。但**没有覆盖"自身"**：agent 底座（Claude/GLM/Kimi 等）与被压缩的 checkpoint（Nemotron/Qwen）是不同的模型。效率方面只约束存储，TPS 不计分且多数情况下变慢。结论：C1 中"agent 驱动压缩"已有很强的先例，"压缩自身"与"真实推理加速"这两点未被覆盖，且作者在结论中把前者列为 future work。
- **C2（LLM 自己产出 LoRA adapter 并应用于自身）**：未涉及。只有少量 agent 在压缩后做 KD 或低秩残差来恢复质量（Kimi、Opus），目的是逼近源模型，不是下游任务适配，也不是应用于 agent 自己。未覆盖。
- **C3（被编辑的模型成为下一轮编辑者，两者共同提升）**：未做。单个 run 内只有对同一源模型的迭代；结论（p.12）明确把"压缩后的模型是否能继续执行压缩任务"留作 RSI 的下一步。未覆盖，但作者已公开提出这个方向，存在被抢先的风险。
- **C4（自我改进作用于权重：压缩操作、adapter、合并）**：动作空间确实是权重层面（量化、剪枝、低秩、蒸馏，外加推理 kernel 代码），这一点与 C4 一致。但它不是"自我"改进（改的是别的模型）。部分覆盖：权重层面的 agent 动作空间已有先例，自我闭环没有。
