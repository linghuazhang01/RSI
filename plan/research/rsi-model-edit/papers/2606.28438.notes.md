## 研究问题
在代码 LLM 的递归自训练中（模型生成代码，代码回流为训练数据，再微调下一代模型），比较三种"审查"机制：
1. 不审查（vanilla）；
2. 外生门（exogenous gate，模拟人类式审查，使用与模型无关的固定规则，如编译、静态质量规则）；
3. AI 自门（AI self-gate，由同一个模型的困惑度或自评分决定接受哪些样本）。
问题是：它们的长期退化轨迹有何不同，什么条件下 AI 自审会退化为"不审查"？

## 方法细节
### 模型（**没有 20B–35B 的模型**）
- SantaCoder 1.1B（主实验）、StarCoder2-3B、Qwen2.5-Coder-1.5B、Code Llama-7B（p2、p7）。都是 base（非 instruct）代码模型，最大 7B。

### 递归自训练协议（§3.1 p7；附录 I、N）
- **谁生成数据**：当前轮的模型自己，从一个固定 prompt 池生成代码（prompt 池的来源与规模在正文和附录中没有说明）。
- **谁验证**：
  - Vanilla：全部接受；
  - Compile（外生）：Python compile() 能通过就接受；
  - Quality（外生）：重复率 ≤0.3 且长度 ≥50 token；
  - Compile+Quality（外生，扩展实验）；
  - Perplexity（AI 自门）：生成 2 万个候选，保留 masked-completion 困惑度最低的 25%；
  - Binary Classifier（AI 自门）：用同一模型计算 log P(good) − log P(bad)，保留得分最高的 25%（附录 H，p25）。
- 每轮接受 5,000 个样本；外生门按每批 2,000 个生成，直到凑够 5,000 个通过的样本；AI 自门固定生成 2 万个保留 25%。
- 每轮微调 3,000 步（Table 10 标注"15k steps"对应 R5，10 轮对应 30k 步）。
- **轮数**：主实验 5 轮；部分扩展到 10 轮（Compile R10、Binary 约 10 轮）；Quality-20R 跑了 20 轮（只有图，没有数值表；Fig. 8，p31）。
- **是否用 LoRA**：正文和附录都**没有提到 LoRA**，只说"fine-tuned for 3,000 steps"，所有方法共享相同训练配置。【推断】看起来是全参数微调，但无法确认。
- 训练数据格式：SantaCoder 用纯代码；StarCoder2 和 Qwen2.5-Coder 用约 70–80% 代码加 20–30% 代码相关自然语言（附录 I）。
- 每轮是否混入原始真实数据：主实验不混入（纯合成）；附录 C.1 做了一个 5% 外部"新鲜已验证锚点"的消融。
- 硬件：NVIDIA RTX 6000 Ada。

### 理论部分
- 把审查形式化为门控重加权：m_gated ∝ m_ungated · r(x,c)（式 2.7，p4）。
- 定理 2.3：如果自门在生成器自身支撑集上的接受分数为常数（"橡皮图章"条件，假设 2.2），门控更新与不门控的 MLE 完全相同（p6）。
- 引理 2.5 / 定理 D.2：AI 审查与外生审查在 L1 距离上的偏差不超过 2ε/(z0−ε)，其中 ε 是最坏情况校准误差，z0 是外生门接受质量的下界（p7、p20）。
- 命题 2.1：在线性化协方差递推 Σ_{t+1}=AΣ_tA^T 下，主特征值比按 ρ^{-2t} 增长，即谱集中（p5）。

## 关键实验与数字
### (c) 递归自训练几轮后崩塌，什么条件下能稳定
- **所有方案在所有模型上都低于各自的第 0 轮基线，没有任何方案能稳定**（Table 2，p8；Fig. 2，p9）。
- **第 1 轮就出现大幅下降**（Tables 11–14，p35–38）：
  - SantaCoder HE+ 0.171 → R1 0.0915（Vanilla），已损失约一半；
  - Qwen2.5-Coder HE+ 0.372 → R1 0.262，MBPP+ 0.582 → R1 0.267；
  - StarCoder2 MBPP+ 0.492 → R1 0.296。
  - 【推断】所以"崩塌"主要发生在第 1 轮，之后是继续缓慢下滑或震荡，并不是若干轮后才突然崩溃。
- **R5 终点**（Table 2，p8）：
  - SantaCoder：Vanilla HE+ 0.073 / MBPP+ 0.019；Compile 0.079/0.034；Binary 0.104/0.058。
  - StarCoder2-3B：Vanilla 0.104/0.172；Quality 0.092/0.098；Binary 0.122/0.066。
  - Qwen2.5-Coder-1.5B：Vanilla 0.043/0.082；Compile 0.098/0.127；Binary 0.122/0.071。
  - Code Llama-7B：Vanilla 0.134/0.214；Compile 0.171/0.090；PPL 0.134/0.175。
- **最严重的情况**：SantaCoder Vanilla 的 MBPP+ 在 R4 跌到 0.008（−97.3%），R5 为 0.019（−93.5%）（p27–28）。Qwen2.5-Coder 的 LiveCodeBench 从 0.238 跌到 R5 的 0.000（附录 M.2，p29）。
- **外生门的作用**：能保住可执行性，但保不住语义正确性。Qwen2.5-Coder R5 下，Compile 把接受集的执行有效率从 33.4% 提升到 89.8%，AI 自门只有 32.0%；HumanEval S5/S0 分别为 0.230（Compile）、0.108（不审查）、0.324（AI 自门）（Table 3，p8）。编译门在 R1 与 R10 的宽松通过率分别为 88.2% 与 89.4%，Vanilla 则从 R1 的 55.4% 降到 R5 的 34.6%（Table 8，p27）。
- **AI 自门的"橡皮图章"现象**：作者在摘要中说 Binary 自门出现接受分数上升而正确性下降，但表中 Binary 的 FPR 恒为 0.250（按构造固定保留 25%），表格里看不到"分数上升"的直接数据。PPL 门的 FPR 从 0.167 升到 0.235（SantaCoder，Table 9，p29），被作者解释为自校准信号退化（附录 K，p27）。Binary 在 SantaCoder 上 MBPP 前期较高、后期骤降（Fig. 8，p31）。
- **门控效果取决于模型和指标，没有统一的最优门**：Binary 在 3/4 个模型上 R5 HE+ 最高，但 MBPP+ 不稳定；StarCoder2 上 Compile/Quality 的 R5 反而低于 Vanilla（附录 M.3，p31）。
- **外部锚点消融**（Table 5，p18）：Synthetic only S5/S0 = 0.364；执行过滤（0% 锚点）= 0.247；执行过滤加 5% 新鲜锚点 = 0.180。作者的结论是 **5% 的外部锚点不足以阻止退化**，而且在这个实验中加锚点后反而更差。论文没有说明这个实验用的是哪个模型。
- **外生门加噪声**（Table 6，p19）：以 5%/10%/20% 的概率翻转门的决策，结果非单调（HumanEval S5/S0 依次为 0.041/0.176/0.257，MBPP 依次为 0.106/0.117/0.049）。作者只把它解读为"对门的校准敏感"。
- **"崩塌吸引子"**：Vanilla R5 时 SantaCoder 和 Qwen 都落在 HE+ 约 0.04–0.10，StarCoder2 和 Code Llama 落在约 0.10–0.14（附录 M.3，p32）。
- **规模/基础的影响**：Code Llama-7B 相对最稳（Vanilla R5 MBPP+ 仍有 0.214）；Qwen2.5-Coder 起点最高、跌得最快（p8、p30）。

## 方法问题与替代解释
- 【推断】**缺少关键对照**：没有"用同样的 3,000 步在真实数据（或原始预训练分布）上微调一轮"的对照。第 1 轮就掉一半，很可能主要来自微调本身（灾难性遗忘或格式漂移，例如 base 模型在纯代码片段上微调后，docstring→函数补全的格式能力下降），而不是"递归"或"自生成数据"造成的。这会严重影响"递归崩塌"的归因。
- 【推断】**单种子，没有统计检验**：轨迹非单调（例如 SantaCoder Binary 的 HE+ 从 R4 的 0.061 回到 R5 的 0.104；Qwen Vanilla 的 MBPP+ 从 R2 的 0.066 回到 R4 的 0.132），说明种子间方差可能与门之间的差异同量级。"哪个门最好"的结论不可靠。
- 【推断】**数据内部不一致**：Table 6 中 σ=0 时接受质量为 1.00，而 Table 3 里同一个 Compile 门的通过率是 0.898；PPL 按构造保留最低的 25%，FPR 却显示为 0.167–0.248，这与"固定保留 25%"矛盾。摘要中"接受分数上升"的说法，在给出的表格里找不到直接证据。
- 【推断】AI 自门固定从 2 万个候选中选样本，外生门按需生成，两者看到的样本数不同；作者虽然报告了候选数，但没有控制这个变量。
- 【推断】理论与实验的连接较弱：定理 2.3 需要接受分数在支撑集上为常数，但实验没有测量自门分数在生成分布上的方差是否趋于 0。
- 【猜测】外生门只检查语法（compile）和长度/重复，根本不检查功能正确性（不运行单元测试），所以"外生门也无法阻止崩塌"的结论，可能只适用于弱外生门；用执行测试（单元测试通过）做门的情况没有作为主实验（Table 5 的"execution-filtered"是例外，但细节不清楚）。

## 对"约 27B 模型自己压缩自己（多轮递归）"研究设计的启示
1. **与本设计的对应关系**：本文研究的是"自生成数据→自训练"的循环；自压缩循环中，与之对应的是"第 k 轮模型（agent）决定如何压缩、并判断压缩结果是否可接受"。论文的核心论点（接受信号如果与被优化的模型耦合，会逐步失去过滤作用）可以直接迁移到"压缩后的模型评判自己的压缩是否成功"的环节。【推断】
2. **如何避免递归崩塌（论文证据支持的部分）**：
   - 接受信号应该是外生且固定的，不随被压缩的模型变化：例如固定的外部 benchmark 测试集、固定的 BF16 参考模型、编译/执行等确定性检查。定理 2.3 说明，模型自评（困惑度、自打分）一旦在自身输出上失去区分度，就等价于不审查。
   - 论文的困惑度自门证据：PPL 门的区分度随轮次漂移（FPR 0.167→0.235）。【推断】在自压缩中，用被压缩模型自己的困惑度判断压缩质量存在同样的风险（2608.06564 也表明困惑度不能定位对工具调用有害的层）。
   - 但论文同时表明，**仅有弱外生门（语法/长度）也不够**：所有方案都低于基线。外生信号需要覆盖功能正确性（本设计中对应 agent/工具调用的实际成功率），而不只是"能跑"。
   - 5% 新鲜数据锚点在本文中没有起作用（Table 5）。【推断】对自压缩来说，"保留少量全精度能力"的锚点策略是否有效，不能从本文得到正面支持。
3. **评测建议**：
   - 如果自压缩 agent 需要写或修改量化代码，可以用 HumanEval+/MBPP+ 和 LiveCodeBench 监测其代码能力（本文显示 LiveCodeBench 这类更难的分布外任务最先归零）。
   - 每轮报告相对第 0 轮的保持率 S_t/S_0、保持面积、斜率，并且必须**多种子**加统计检验（本文的单种子设计是明显的弱点）。
   - 必须设置"非递归"对照（例如每轮都从原始模型出发做同等强度的单次压缩），把"递归累积"与"单步压缩损伤"区分开（本文缺少类似对照，因此难以归因）。【推断】
4. **模型规模提示**：本文最大只有 7B；Code Llama-7B 最稳、更强的模型崩得更慢（附录 M，p30 的作者陈述）。【推断】27B 模型可能退化更慢，但本文没有提供 20B+ 的证据。
