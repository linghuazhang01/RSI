## 研究问题
现有自我改进方法里，"怎么改进模型"的策略仍由人设计。LLM 能不能自己发明改进模型的算法（以 Python 代码形式），用这些算法提升模型，同时通过训练让自己越来越会发明这类算法？在不借助更强外部模型（如 GPT-4）的前提下能否做到？

## 方法细节
- **框架**（p2–p4，Fig. 2，Alg. 1 在 p21）：
  1. 初始化：algorithm factory π^g_1 = 种子模型 M0 的拷贝。
  2. 生成：π^g_t 根据固定 prompt x（含 one-shot 示例，Fig. 12/13）采样 N 个 Python 函数 merge_models(model_dict, device)。
  3. 评估：去掉不可执行或超时的函数；把每个算法作用于各候选模型的任务向量 τ_Cj = C_j − M0，得到合并后的任务向量 τ_t = a_t(τ_C1..τ_CK)（式 1），再得 M_t = M0 + τ_t（式 2）；在 dev 集上算分 s_t。
  4. 改进 factory：取分数前 p_w%（chosen）和后 p_l%（rejected）构造偏好对（式 3），用 DPO 训练 π^g_t 得到 π^g_{t+1}；从第 2 轮起，把之前各轮的 top-3 算法加入 chosen。
  5. 迭代，同时按 T_t = T1 / (1 + β(t−1)) 降低采样温度（式 4，附录 B）。
- **谁在修改谁的权重**：算法 factory（M0 的拷贝，后续被 DPO 更新）写代码，代码把**外部的三个微调模型**的任务向量合并到 **M0**（固定的种子模型）上。factory 和被修改的 M0 是同源但分离的两个实体。p4 §2.4 明确说生成的算法**总是作用于 M0**。factory 自身的权重由 DPO 更新，这一步由框架驱动，factory 并不对自己执行合并。
- **修改形式**：**写可执行代码**（Python 模型合并函数），在 mergekit 中作用于每个 MLP 层的任务向量（p5）。不生成训练数据，不直接生成权重，也不涉及压缩配置。
- **是否多轮递归**：factory 多轮递归改进（3 轮，每轮 3000 个候选，过滤后约 100–300 个可执行，p5 及脚注 8）。但**合并得到的改进模型 M_t 不会成为下一轮的 factory**；下一轮 factory 是 DPO 更新后的 π^g_{t+1}，被修改对象始终是原始 M0。作者把这称为"同时改进 factory 和种子模型"（Fig. 1 说明、p4），实际上 seed 的"改进"每轮都是从 M0 重新合并，不累积。
- **模型**：
  - 种子 M0：openchat-3.5-1210（Mistral-7B 微调版，代码能力强）。
  - 合并候选：Abel-7B-002（数学）、OpenHermes-2.5-Mistral-7B（代码指令）、SciPhi-Mistral-7B-32k（科学）（p5）。
  - 迁移实验的新候选：WizardMath-7B-V1.1、Starling-LM-7B-alpha、BioMistral-7B（p7）。
- **数据/任务**：
  - GSM8k：从测试集划出 100 题作 dev，其余 1220 题作 test。
  - MATH：每个子集 100 题，共 600 题作 dev，其余 4400 题作 test。
  - 评估用 lm-eval-harness，5-shot，greedy，exact match（p5）。
- **训练协议**：DPO 中 p_w = 3%，p_l = 10%；LoRA r=256 训练 factory 的所有线性层；lr 1e-6，β 0.01，最多 5000 步；温度 T1 = 1.2，β = 0.2，到 T3 ≈ 0.85（p5）。最终在 test 上只评估 dev 上排名前 15 的模型。
- **基线**：Task Arithmetic 和 TIES，混合比例在 {20%, 40%, 60%} 上穷举，按 dev 选最优；另有 Model Stock（p5）。

## 方法问题与替代解释
- 【推断】**搜索预算不对等**：LLM 侧每轮 3000 个候选、约 100–300 个可执行，3 轮共数百个合并模型在 100 题的 dev 上择优；Task Arithmetic 只穷举 3^3 = 27 种比例。dev 只有 100 题，在数百个候选里择优，存在明显的选择偏倚或过拟合风险。test 上 top-15 的分数几乎相同（76.0–76.1），也和"多个近似配置撞到同一个点"相符。
- 【推断】**最优算法的实际含义很简单**：算法 A（Fig. 11，p19）大致相当于把第一个候选（字典顺序中的 Abel）的任务向量缩小到约 0.25 倍，再加上其余候选按行求均值的项。它很可能等价于"Abel 任务向量取一个小系数"，而这个系数在 Task Arithmetic 的 20/40/60% 网格之外。所以收益未必来自"新颖算法"，可能只是搜索到了网格外的缩放系数。J、K（Fig. 22–23）本质是简单平均，MATH 上却有 8.41。
- 【推断】**MATH 基线异常**：种子模型 MATH 只有 0.5%，而简单合并就能到 8%，很可能反映 5-shot 输出格式或答案抽取问题被合并"修复"，不代表推理能力提升。迁移实验中 MATH 上发现的算法在新候选上几乎为 0（Table 4），也说明它们没有学到通用改进。
- 【推断】**"递归"改进主要体现在 factory 的输出分布上**：Table 2 中 GSM8k 第 1 轮（未经 DPO 的 M0 直接生成）已到 75.8，三轮 DPO 后只多 0.3 个点；MATH 的 7.0 → 8.5 也在 dev 择优的噪声范围内，没有方差或多种子报告。
- 【推断】种子 M0 每轮都从头重新合并，改进模型不会反哺 factory，也不会作为下一轮的起点。因此"种子与 factory 共同提升"的说法比实际机制更强。
- 【推断】迁移结果 78.8 只比单模型 Starling（75.5）高 3.3 点，而合并时 Starling 的任务向量占主导的可能性较大。
- 【猜测】prompt 里写死了候选模型名和描述（Fig. 13），factory 生成的代码有时按模型名硬编码权重（Fig. 3），这类算法的"迁移"其实依赖字典顺序。

## 与每个 core claim 的关系
- **C1 自主压缩（量化/剪枝）以提效**：**未覆盖**。动作是模型合并，目标是任务准确率，不涉及推理效率、量化或剪枝。
- **C2 自主产出下游任务 LoRA 并作用于自己**：**未覆盖**。没有生成训练数据或 LoRA；LoRA 只用于 DPO 训练 factory（由框架完成）。合并的是外部现成的全参微调模型的任务向量。可以视为一种"自主选择或组合已有专家权重"的相邻形式，但不是为下游任务自产 adapter。
- **C3 递归闭环**：**部分覆盖**。factory 经 3 轮 DPO 递归提升"写改进算法"的能力，作者自称首个同时改进算法和生成算法的 LLM 的递归自我改进工作（p10）。但：(a) 被合并后的改进模型不会成为下一轮的编辑者，被修改对象始终是固定的 M0；(b) factory 的更新是外部 DPO 管线，不是 factory 对自己执行合并；(c) 只有 3 轮，GSM8k 上逐轮收益很小。所以不满足"被编辑模型即下一轮编辑者"这一严格形态。
- **C4 权重级动作空间**：**覆盖（以合并的形式）**。动作是写直接操作权重张量（任务向量）的代码，属于权重空间操作（合并），而不是 prompt 或外部框架。但只覆盖合并一种算子，且只作用于 MLP 层；不含压缩或 adapter 生成。
