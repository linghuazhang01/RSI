## 研究问题
- 自我改进研究分成两支：只改 harness（scaffold）、权重不动（DGM、Meta-Harness、Hyperagents）；以及人写 RL 流水线、在测试时更新权重、harness 不动（TTRL、Discover-TTT）。作者把这称作两个"silo"（p1–p2）。
- RQ1：在 harness 迭代基础上再做权重更新，能不能突破 harness-only 的上限？这个结论在不同领域是否成立？RQ2：两种手段分别改变了什么（p3）？

## 方法细节
- **三个组件**（p3, p6, p8）：
  - Meta-Agent M：根据任务说明 U 和参考实现 R 生成初始 scaffold，即 A1 = M(U, R)。
  - Task-Specific Agent：在 scaffold 中执行任务的模型，基座是 **gpt-oss-120b**（预训练且经过对齐的开源模型）。
  - Feedback-Agent F：读取完整轨迹 τg、指标 Eg 和当前 scaffold，每一步在两种动作中选一种：(a) harness 更新，A_{g+1} = F(A_g, τ_g(π_θ), E_g, U)，权重固定；(b) 权重更新，用 F 选定的 RL 算法训练 LoRA，scaffold 固定（p6, p8）。
  - **Meta-Agent 和 Feedback-Agent 都是 Claude Sonnet 4.6**（p8）。
- **谁修改谁的权重**：一个外部、冻结的模型（Claude Sonnet 4.6 当 Feedback-Agent）决定什么时候训练、用哪种算法，被训练的是**另一个模型** gpt-oss-120b 的 LoRA。这不是"同一模型改自己"。RL 用的 rollout 由目标模型自己生成（on-policy），奖励来自确定性的任务 verifier。
- **修改形式**：LoRA rank 32，lr 4e-5（p5, p8）。RL 算法由 F 选择：LawBench 用 PPO+GAE（p9），TriMul 用 entropic advantage weighting（p10，引用 Yuksekgonul 2026），去噪任务用 GRPO（p11）。§7.3（p12）还列出了"更广泛实验中观察到"的 REINFORCE+KL、Best-of-N BC、DPO，但没有给出对应数据。训练通过 Modal 平台执行。作者说 F 对这些基础设施组件做"组合"（p5），论文没有说明 F 是否真的自己写训练代码。
- **压缩/量化/剪枝/推理效率**：完全没有涉及。TriMul 任务优化的是生成的 CUDA kernel 的运行时间，是"任务产物"的效率，不是模型自身的推理效率。
- **是否多轮递归**：harness 和权重会交替更新（Fig. 2b 示意了 H/H/W/H/W/W，p7），但 **Feedback-Agent 本身从不更新**。被训练的 gpt-oss 也不会变成下一轮的修改者。作者在 Future Work（p13）中明确说，让选择策略本身可学习才会构成真正的递归结构，并把这列为未来工作。实际实验的流程是：先做 harness 迭代，平台期后切换到权重更新（p8–p9）。

## 关键实验与数字
- Table 2（p8）：三个任务。LawBench 191 类（train 5,332 / test 913，先前 SOTA 0.450）；AlphaEvolve TriMul（score=1500/runtime，先前 SOTA 1.292）；MAGIC scRNA 去噪（mse norm，先前 SOTA 0.24）。
- **Table 3（p11）主表**：
  - LawBench top-1：初始 13.5%，SIA-H 50.0%，SIA-W+H **70.1%**（先前 SOTA 45.0%）。
  - TriMul reward：初始 0.105，SIA-H 0.120，SIA-W+H **1.475**（先前 SOTA 1.292），对应 runtime 1,017 vs 1,161 µs（摘要 p1、p2）。
  - 去噪 mse norm：初始 0.048，SIA-H 0.241，SIA-W+H **0.289**（先前 SOTA 0.240）。
- p9：LawBench 的 harness 阶段把方案改成了 TF-IDF + LinearSVC，比初始提升 36.5pp，然后 PPO 再加 20.1pp。
- p10：TriMul 最终加速 14.02×，相对 harness-only 峰值 runtime 降低 91.9%（12,483 → 1,017）。
- p11：去噪任务中，GRPO 后的第一个 checkpoint 引入了 np.clip + np.rint 后处理，带来约 20% 提升。
- Fig. 1、4、5、6（p2, p9, p10, p11）是上述数字的柱状图。

## 作者自己声明的局限（p13）
- 只有一条："耦合协同进化 Goodhart"。harness 搜索和 RL 都针对同一个固定 verifier 优化，二者的不动点在训练 verifier 上可能看起来很强，但对任一组件的扰动都很脆弱。
- §7.3（p12）承认，算法选择的系统性分析要推迟到 v2。

## 方法问题与替代解释
- 【推断】**没有方差，没有重复**：每个任务只报告一次运行的最好值，没有种子数，也没有 CI。
- 【推断】**测试集泄漏风险**：p9 写的是 LawBench 的 rollout 是"生成的解题脚本，在 test split 上执行"，奖励也来自 held-out test split grader（Table 2）。如果 RL 奖励直接用测试集准确率，70.1% 就是在测试集上做优化的结果，不能和先前 SOTA 直接比较。
- 【推断】"权重带来领域直觉"这一说法和任务本身混在一起：LawBench 中模型写的是分类脚本（TF-IDF+SVC），RL 优化的是"写脚本"的策略，而不是模型对法律的理解。去噪任务的提升来自一个两行的后处理技巧，这同样可能是搜索预算或随机性造成的，不一定是权重更新独有的能力。
- 【推断】**对照不公平**：W+H 比 H 多花了一个阶段的计算（RL），却没有"同等预算继续做 harness 迭代"或"只做 RL"的对照。
- 【猜测】TriMul 的 harness-only 结果（0.120）远低于先前 SOTA，而 RL 后跳到 1.475，提升幅度很大，但论文没有给出 RL 步数、rollout 数或计算量。
- 数字上存在小的不一致：p10 把"12,483"称为 best runtime，同时又叫 1.14× speedup，单位没有统一说明。

## 与每个 core claim 的关系
- **C1（自主压缩自身权重，追求推理效率）**：**没有涉及**。全文没有量化、剪枝、蒸馏或推理效率目标。
- **C2（模型自己产出下游任务 LoRA 并装到自己身上）**：**部分相邻，但不覆盖**。它确实为下游任务产出了 LoRA（rank 32），用的是目标模型自己的 rollout 加 RL，但决定和执行训练的是**另一个模型**（Claude Sonnet 4.6）。目标模型 gpt-oss 不决定也不编写自己的训练流程。LoRA 的产生方式是 RL，没有"生成训练数据集 + SFT"，也没有"直接生成权重"。
- **C3（被编辑的模型成为下一轮编辑者，形成递归）**：**没有覆盖**。Feedback-Agent 固定不变，被训练的模型不承担编辑者角色。作者把这种递归明确列为未来工作（p13）。
- **C4（动作空间在权重层面）**：**部分覆盖**。动作空间是 harness 加权重（LoRA RL），权重更新是一个可选动作。但它不包括压缩算子或 adapter merging，权重动作的形式只有"选一种 RL 算法训练 LoRA"。
