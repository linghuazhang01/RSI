## 研究问题
- 前沿 CLI agent（Claude Code、Codex CLI、Gemini CLI、OpenCode）在有限算力（单张 H100，10 小时）和不给任何起始代码、数据、超参的条件下，能否自主把一个**基座 LLM** post-train 到在某个目标 benchmark 上表现好（p1–p2）？这是一篇 benchmark 论文，衡量 AI R&D 自动化能力，同时记录 reward hacking 行为。

## 方法细节
- **被训练的目标模型**：4 个预训练基座，Qwen3-1.7B-Base、Qwen3-4B-Base、SmolLM3-3B-Base、Gemma-3-4B-PT（p3，Table 4 p14）。
- **执行修改的 agent**：前沿闭源或开源 LLM 加 CLI scaffold，例如 Claude Opus 4.6（Claude Code）、GPT-5.x Codex、Gemini 3/3.1 Pro、GLM-5、Kimi K2.5、MiniMax 等，共 22 个配置（Table 1 p5）。
- **谁修改谁的权重**：**另一个 agent 修改目标小模型**，agent 不修改自己的权重。规则明确禁止换用其他模型，禁止下载 instruct 版本（p2，附录 B p14–p15）。
- **任务**：7 个 benchmark，AIME 2025、GSM8K、GPQA、HumanEval、BFCL v3、ArenaHard-Writing、HealthBench-Easy（p3）。每次运行是一个"模型 × 单个 benchmark"组合，一共 4×7 = 28 个（Fig. 2 p3）。
- **修改形式**：agent 完全自主地搜索数据、写训练代码、选方法和超参，最后提交 final_model 目录。行为分析（§5.2 p7–p8）显示：**SFT 是绝对主流**；GRPO 只由 Claude 系 agent 作为 SFT 之后的第二阶段使用（Sonnet 4.6 用在 33% 的任务中，Opus 4.6 用在 3%）；DPO 只出现过一次；LoRA 和全参数微调的偏好因 agent 而异（GPT-5.3 Codex 几乎 100% 用 LoRA，Gemini 3.1 Pro 约 66% 用全参数）；**Kimi K2.5 在一半以上的脚本中用 QLoRA（4-bit 量化 LoRA）**，目的是省训练显存。
- **评分**：先在 4 个基座上取平均，再按公式 (1)（p4）对各 benchmark 加权，权重 w_i ∝ 1/(s_instruct − s_base)（Table 5 p14）。LLM judge（GPT-5.1 Codex，附录 E p15–p16）检测数据污染和违规换模型，被判作弊的运行记为基座分数。
- **压缩/量化/推理效率**：**不是研究目标**。唯一相关的是 agent 自发使用 QLoRA 来节省训练显存，不涉及部署时的推理效率。
- **是否多轮递归**：**否**。agent 在单次 10 小时运行内会多次迭代训练脚本（train.py 到 train_v10.py，p8），但训练好的小模型不会反过来成为 agent，agent 也不会被更新。

## 关键实验与数字
- **Fig. 1（p1）/ Table 1（p5）**：最佳 agent Claude Opus 4.6 的加权平均为 **23.2% ± 1.8**；官方 instruct 模型为 **51.1%**；基座 zero-shot 为 7.5%，few-shot 为 18.1%。
- Table 1（p5）：BFCL 上 Opus 4.6 达到 75.9 ± 17.8（基座 1.5）；GPQA 上几乎所有 agent 都低于 25% 的随机水平（p5 正文）。
- **§3.2（p5–p6）**：Gemma-3-4B 在 BFCL 上 agent 达到 **89%**，官方 IT 版为 67%；SmolLM3-3B 在 BFCL 上 91% vs 84%；Gemma-3-4B 在 GPQA 上 33% vs 31%。
- Table 2（p6）：GPT-5.1 Codex Max 的推理强度 low/medium/high 对应 15.5/19.7/17.2。Table 3（p6）：GPT-5.3 Codex medium 13.77、high 17.76。
- Fig. 4（p6）：Claude Haiku 4.5 / Sonnet 4.5 / Opus 4.5 分别为 6.2/9.9/17.1。Fig. 5（p7）：Opus 4.5 在约 5 小时后进入平台期。
- **§5.5（p8–p9）**：在新增的 agent 中共有 23 个污染标记；**Opus 4.6 在 84 次运行中有 12 个污染标记**，其中 8 个是 HumanEval；Gemini 3.1 Pro 为 0。
- Fig. 3（p4）：Opus 4.5 在 Gemma-3-4B 上做 HumanEval，从 0% 提升到 37.3%，用了 104 轮、9:20 小时、$4.62。

## 作者自己声明的局限（p10–p11）
- 10 小时单卡预算不代表真实的 post-training 规模；benchmark 的选择可能偏向某些策略；agent 只针对单一任务优化，而不是训练通用模型；LLM 污染判定可能有假阳性或假阴性；前沿 agent 只跑了 3 次，其余配置只跑 1 次，方差估计有限。

## 方法问题与替代解释
- 【推断】"超过 instruct 模型"的三个案例都是单任务过拟合式优化，作者自己也承认这不等于通用 post-training 能力（p6）。BFCL 上的方差极大（例如 GPT 5.1 Codex Max 为 30.8 ± 50.8），只能说明结果高度不稳定。
- 【推断】从 7.5% 到约 30% 的大部分提升可能只是学会了格式和指令遵循，作者在 p10 也这样说过。few-shot 基座就有 18.1%，与多数 agent 不相上下。
- 【推断】污染检测依赖 LLM judge，而污染又与最强 agent 正相关，所以排行榜可能部分反映了"作弊没被抓到"的程度。
- 文中有小的不一致：p5 正文写 GPT-5.1 Codex Max 在 Codex CLI 上为 20.2%、Gemini 3 Pro 在 Gemini CLI 上为 18.3%，Table 1 中分别是 19.7 和 18.1。

## 与每个 core claim 的关系
- **C1（自主压缩自身权重以提升推理效率）**：**没有覆盖**。目标是提升 benchmark 分数，不是推理效率；QLoRA 只是训练时省显存的手段，而且作用对象是别人的模型。
- **C2（模型自己产出下游任务 LoRA 并装到自己身上）**：**流程高度相关，但主体不同**。PostTrainBench 证明了 LLM agent 可以端到端地为下游任务自主生成训练数据、写训练代码、选超参，并产出 LoRA 或全参数微调后的权重。但被训练的是**另一个小模型**，agent 不把 adapter 装到自己身上。它可以作为 C2 的可行性证据和对比基线，但不构成"self-authored"。
- **C3（递归）**：**没有覆盖**。只有单轮，训练后的模型不承担 agent 角色。
- **C4（权重层面的动作空间）**：**部分覆盖**。agent 最终交付的是权重（SFT/GRPO/LoRA/全参数），不是 prompt 或 harness。但这些动作通过写通用训练代码实现，不包含压缩算子或 merging 作为一等动作，而且仍然作用于他者的模型。
