## 0. 一页摘要

**候选标题**
- *Who Compresses the Compressor? Recursive Self-Quantization of Language Models*
- *When the Compressor Is the Compressed*

**一句话卖点**：到了最前沿，没有更强的模型可以替你压缩，模型只能压缩自己。我们测量这个闭环能走多远，以及它在哪里停下、为什么停下。

**设定**：一个 27B 模型在存储预算下为自己的权重做量化决策，包括逐模块比特数、量化器、group size 和校准数据。产物通过固定的外部验收后，接任下一轮的压缩者。全过程不借助任何更大的外部模型。

**研究问题**
- **RQ1（单轮）**：不借助更强的模型，27B 能否为自己做出不差于统一量化和非 LLM 分配器的量化决策？
- **RQ2（递归，核心）**：量化后的模型当压缩者，后续压缩决策会怎样变化？递归在哪里停下，原因是预算变紧、重复量化，还是压缩者自身退化？
- **RQ3（机制）**：最先坏掉的是哪种能力？模型会自己学会保护哪些模块？

**我们要检验的主张**（结果出来前都是假设）
1. 自压缩闭环能稳定走过若干代，用"自压缩深度"度量。
2. 2×2 对照能把递归损伤拆成三部分：预算变紧、重复量化、压缩者退化。
3. 压缩者退化首先表现为工具调用能力（尤其是"要不要调用工具"）受损，而 PPL 看不出来。

**我们不主张的**：
- "首次 agent 驱动的压缩"，CompressionBench 已经做了；
- "首次更新后的模型接任"，MASS 已经做了；
- 新的量化算法。

## 2. 方法

### 2.1 递归闭环与符号

```
S      = 同一模型的 BF16 源权重（只读）
B_t    = 第 t 轮的存储预算
M_0    = BF16 原模型；M_t = 第 t 轮验收通过的量化模型

第 t 轮：
  压缩者 = M_t（由 vLLM 加载 M_t 的量化产物来运行 agent）
  被压缩对象 = S（主设计）
  1. 压缩者阅读反馈历史，调用 profile 查看敏感度
  2. 提出配置 → quantize → evaluate，得到 L1 反馈
     每轮最多 N = 24 个候选，或 G GPU 小时，以先到者为准
  3. 选最优候选 submit → L2 验收门，每轮最多提交 3 次
  4. 通过 → M_{t+1}，下一轮当压缩者；
     不通过 → 记为停止点，即递归边界
```

**为什么主设计每轮都从 S 出发**：在已量化的权重上再量化会叠加舍入误差，这种误差和"压缩者变笨了"混在一起无法分开。从 S 出发，递归只体现在压缩者换成了压缩后的自己。"在上一轮量化权重上继续压"作为 2×2 中的一臂（§4 的 E3）。

**预算序列**（主设计）：

| 轮次 | 产物 | 预算 | 约合 bits/参数（含 scale、embedding 等开销） |
|---|---|---|---|
| 0 → 1 | M_1 | 16 GiB | 5.09 |
| 1 → 2 | M_2 | 12 GiB | 3.82 |
| 2 → 3 | M_3 | 10 GiB | 3.18 |
| 3 → 4 | M_4 | 8 GiB | 2.55，压力测试 |

注意 16 GiB 不是 16-bit。为了画出更细的自压缩深度曲线，可选加一个细粒度序列 16 → 14 → 12 → 11 → 10 → 9 → 8 GiB，前提是 A-P2 的算力有剩余。

### 2.2 核心指标的定义

**压缩者能力 E_t**：让 M_t 完成一个**不随代数变化**的固定任务：在 12 GiB 下压缩 S，给 24 个候选的评估预算，工具、初始 prompt 和校准数据池都固定。每次测 E_t 都开一个新会话，不进入主循环的历史。

| 指标 | 定义 |
|---|---|
| E_t 主指标 | 最终提交产物在**留出 KL 集**上的超额 KL。留出 KL 集是从五个领域留出集的题面中取的 256 段上下文，循环永远看不到；L1 的 KL 上下文只取自训练集的 `train` 池 |
| E_t 辅助指标 | 合法配置比例、可运行比例、L2 通过率、首次通过所用的 GPU 小时、工具调用失败次数 |

主循环里的预算逐轮收紧，所以只看主循环无法区分"压缩者变差了"和"预算变紧了"。把 E_t 固定在 12 GiB 就是为了分开这两者。

**自压缩深度 D**：按主预算序列递归时，满足以下条件的最大连续轮数：每个能力类别（数学、代码、闭卷知识、指令遵循、工具调用）在 L3 上的分数都不低于第 0 代的 95%。
- 这个阈值的写法借鉴 LLM-KICK，它把"掉点 ≤5%"定义为 matching。
- D 在 L3 上事后计算，编辑者看不到。
- L2 验收门比 5% 宽松（§2.5），所以递归可能继续走，但 D 已经停止增加。两者的差就是"验收门没拦住的隐性退化"，本身也是一个结果。

**其他指标**：
- 配对翻转率：同一题在 BF16 和量化模型上"调用 / 不调用"的判断是否翻转（Which Decisions 的口径）。
- 工具调用的错误类型：该调用没调用、不该调用却调用、函数名幻觉、参数错误、JSON 格式错误，分开统计。
- 效率：包大小、常驻显存、峰值显存、TTFT、decode TPS（batch 1 和 32）。
- 输出长度和重复率：3-bit 崩溃时会反复输出同一段。

### 2.3 动作空间

**Level 1（主实验）**：
- 每个模块组的比特数 ∈ {3, 4, 8}，8 GiB 时加入 2。每层分 5 组：{q, k}（两者有强交互，OWQ Tab.13）、v、o、{gate, up}、down；
- group size ∈ {32, 64, 128}；
- 量化器 ∈ {GPTQ, AWQ, RTN}；
- embedding / 输出头精度 ∈ {4, 8, 16}；
- 校准数据来源 ∈ {C4, FineWeb, 自己生成, 推理类数据}，条数 ∈ {128, 512}。

**固定不变的**：
- 激活和 KV cache 保持 16/8 bit。A4 会毁掉工具调用决策（Which Decisions Fig.5）；W4A4KV4 时 32B 也掉 2.9（Quant Hurts Reasoning Table 1）。
- 只允许 vLLM 有高效 kernel 的格式。CompressionBench pilot 中混合 3/4 bit 能跑到 110.8 TPS（Table A4），但具体 kernel 组合要在 A-P0 实测。

**Level 2（扩展，A-P3）**：允许在受限 API 内写新的量化代码，例如旋转或 trellis 编码，参照 CompressionBench 中 Sonnet 的方案。

### 2.4 工具与 agent 外壳

| 工具 | 返回 | 是否计入预算 |
|---|---|---|
| 预算好的诊断表：`profile_table`（RTN 伪量化下各模块组的整模型 ΔKL）、`activation_table`（激活与离群统计、红旗模块）、`behavior_sensitivity`（各模块组单独降到 3-bit 时工具调用 margin 的变化）、`bytes(config)` | 由固定程序生成，所有代相同 | 不计入 |
| `profile_in_context(group, bits, quantizer, base_config)` | 在当前配置上下文中重测 ΔKL；平均比特 ≤ 3 或用到 2-bit 时必须用 | 计入 |
| `evaluate(config)` | 真实量化后的整模型 KL、字节数、行为探针，即 L1 反馈（结构化 JSON） | 计入，每轮最多 24 次 |
| `solve_allocation(weights, budget)` | 按编辑者设定的目标权重求解比特分配；主条件可用，消融时去掉 | 不计入 |
| `submit(config)` | L2 的通过 / 不通过和粗粒度原因 | 每轮最多 3 次 |

编辑者写一段 Python 程序，读入诊断表和历史，返回配置；校验器检查预算和合法性。设计理由见 `METHOD_DESIGN.md` §2。

**外壳**：开源编码 agent 外壳，例如 qwen-code（MASS 用过）或 mini-SWE-agent（Self-HPO 用过）。所有代码在沙箱里执行：无网络、限时、只能调用白名单 API。外壳、system prompt 和反馈格式在所有代之间保持不变，否则 E_t 的变化无法归因。

### 2.5 三层反馈

文献给出两条硬约束：
1. **不能用模型自评。** Anosognosia 显示，模型从自己的输出看不出自己被量化过；When AI Reviews Its Own Code 证明自评门会逐代退化（定理 2.3）。
2. **不能只看 PPL 或总分。** CompressionBench 中，Opus 在 27B/8 GiB 上 PPL 一路下降，GSM8K 却从 88% 掉到 72%。Flat Score 中 INT4 的总分不显著变化，但失败预算收紧到 K=2 后，差距从 1.3 扩大到 16.7。

| 层 | 编辑者看到什么 | 内容 |
|---|---|---|
| **L1 搜索反馈** | 具体数字、2–3 条错误样例、历史候选记录 | 超额 KL / PPL 比（CompressionBench 做法：256 段 × 512 token 上下文，BF16 续写 1,536 token；上下文取自五个训练集的 `train` 池，并加入 BF16 模型在训练集题目上的自生成推理文本，依据是 2504.04823：3-bit GPTQ 用推理类校准数据比 WikiText2 平均高 9.8）；实际包大小和常驻显存；batch=1 decode TPS；各领域训练集**信号切片**（`search` 池）上的任务分数，见 §3.3。具体给哪些诊断信息，以 `METHOD_DESIGN.md` 的结论为准 |
| **L2 验收门** | 只有"通过 / 不通过"和粗粒度原因 | 各领域训练集的**验收切片**（`gate` 池），见下表 |
| **L3 留出评测** | 永远看不到 | §3.3 中的全部留出集；每代结束后评测，只用于报告，不用于挑候选 |

**L2 验收门**（门槛都相对**第 0 代**，不相对上一代，否则每代允许的小退化会累积）：

| 条件 | 默认值（A-P0 后预先登记最终值） |
|---|---|
| 数学（GSM8K train + MATH train 验收切片各 200）、代码（APPS 验收切片 200，执行测试用例）、知识（TriviaQA train + ARC 验收切片各 200、GPQA Main 125）的平均分 | ≥ 0.8 × 第 0 代。门槛沿用 CompressionBench，但题目从 benchmark 换成训练集切片 |
| 每个类别各自的下限 | 不低于第 0 代的 0.7 倍（假设），防止平均分掩盖单项崩溃 |
| 工具调用：Seal-Tools train 验收切片 200 题的完全正确率；加上构造的"不该调用"样例上的误调用率（见 §11） | 正确率 ≥ 0.9 × 第 0 代；误调用率上升 ≤ 预设值 |
| 指令遵循：IFEval 验收切片 135 条 | ≥ 0.9 × 第 0 代（假设） |
| 存储 | ≤ B_t |

每个门槛都要比第 0 代模型在同一切片上重复跑 3 次的波动范围宽，否则判定只反映噪声（RRSI 的做法，A-P0 实测）。

**补充规则**：
- **回滚**：候选造成严重退化时直接丢弃，并把失败写进反馈历史。可以借鉴 Adaptive Pruning 的做法：单轮 PPL 上涨超过 15% 就回滚。
- **评测器不随模型变化**：BF16 参考输出和判分程序都固定。
- **主实验只用确定性判分**：精确匹配、单元测试、执行结果，不用 LLM judge。

## 3. 实验设置

### 3.1 模型

| 用途 | 模型 | 理由 |
|---|---|---|
| 主实验 | **Qwen3.8 27B（dense）** | CompressionBench 用它做 dense 任务，BF16 参考值、统一 GPTQ、已发布量化版本和 6 个前沿 agent 的结果都能直接引用 |
| 备选 | Qwen3.6-27B | 主模型在 agent 外壳里跑不稳时换它；MASS 已证明它能作为编码 agent 跑通 |
| 跨家族泛化（A-P3） | Gemma-4-31B | Flat Score 中它在 INT4 下工具名幻觉率从 19.5% 翻到 38.3%，Qwen-3.6-27B 几乎不变，可以作为量化敏感模型的对照 |

Flat Score 显示，同为 27B 的 Qwen-3.6 和 Qwen-3.5 对 INT4 的耐受度不同，所以 A-P0 必须在实际选用的 checkpoint 上跑。

### 3.2 基础设施
- 服务：vLLM。
- 量化执行：llm-compressor、GPTQModel 等现成库。
- 评测：统一放在项目根目录的 `eval/`，入口是 `eval/run_eval.py`；它通过 OpenAI 兼容接口访问 vLLM 服务的模型，并按题目保存打分，供配对 bootstrap 使用。
- 日志：保存每个候选的配置、反馈、耗时和 token 数，用于分析压缩者行为。

### 3.3 数据与切分

总原则：**循环只看训练集，benchmark 全部留出。** 每个领域一份训练集，切成 `search`（L1 信号，200 题）、`gate`（L2 验收，200 题）和 `train`（KL 上下文与校准文本）；benchmark 全部放在 `test` 池，只进 L3。这个分法来自 RSI 文献调研（`plan/research/method-research/rsi-data/RSI_DATA.md`）：直接在测试题上搜索会高估增益，例如 DGM 在搜索用的 50 题上 +24.0，换到全集只剩 +16.5；从同一 benchmark 切小 dev 也会过拟合，例如 EvoGM 用 70 题 MMLU-Pro 验证集，验证 0.429，测试只有 0.224。切分规则、计数和去污染见 `data/README.md`。

| 领域 | 训练集 → L1 信号 / L2 验收 | L3 留出集（主表） | 训练集的文献依据 |
|---|---|---|---|
| 分布对齐 | 训练集 `train` 池题面 + BF16 自生成推理文本 → 256 段 KL 上下文 | 留出集题面中另取 256 段 → **E_t 主指标** | CompressionBench 的 KL 做法；2504.04823 |
| 数学 | GSM8K train、MATH train、DAPO-Math-17K（去污染后 16,329 题）：L1 取 MATH train + DAPO 信号切片各 100；L2 取 GSM8K train + MATH train 验收切片各 200 | **MATH-500**；**AIME 2024+2025**（60 题，每题采样 8 次取平均）；GSM8K test 1,319 | ReST-EM、WSP 博客 / WSP-Scope、WHALE |
| 代码 | APPS 入门级 train（2,397 题，带测试用例）：L1 信号切片 100，L2 验收切片 200 | HumanEval+ 164；MBPP+ 378；LiveCodeBench 131（2025-02-01 之后） | ReST-EM |
| 闭卷知识 | TriviaQA train、ARC train、GPQA Main 去掉 Diamond：L1 取 TriviaQA + ARC 信号切片各 100；L2 取两者验收切片各 200，再加 GPQA Main 125 | **TriviaQA 闭卷** 2,000；GPQA-Diamond 198；MMLU-Pro 2,000 | Transformer²（ARC）；WSP-Scope（GPQA Main）；TriviaQA train 无 RSI 先例 |
| 指令遵循 | IFEval 的 270 条：L1 信号 135，L2 验收 135 | IFEval 其余 271；IFBench 300（领域外） | WSP-Scope 的 270/271 切法 |
| 工具调用 | Seal-Tools train：L1 信号切片 200，L2 验收切片 200；ToolACE 对话只用作 KL 上下文 | **Seal-Tools test**（in-domain 700 + out-domain 654）；**BFCL**（irrelevance 与 live_simple 分开报）；API-Bank test 584 | TT-SI 的 SFT 基线；ToolACE 作工具调用校准来自 2608.06564 |
| **自压缩任务** | — | 在 12 GiB 下压缩 S，每代测一次 | **E_t** |

额外留出集（附录）：AMC23、OlympiadBench、FreebaseQA、MetaTool、T-Eval。MT-Bench、AlpacaEval 2 需要 LLM judge，不进主结果。

**主打任务**：MATH-500 / AIME（推理）、TriviaQA 闭卷（知识）、BFCL 和 Seal-Tools（工具调用），再加上自压缩任务本身。这几类都对量化敏感；代码和指令遵循作为门槛和保底。工具调用和代码能力直接决定"压缩后的模型还能不能继续压缩"，正好串起递归这条主线。

**两处只能靠推断的地方**（论文里要写明）：
- 指令遵循的信号和留出集都来自 IFEval，只能防止记住具体题目，防不住适应 IFEval 本身，所以必须报告 IFBench；
- TriviaQA train 当闭卷知识信号没有 RSI 先例。

## 4. 实验矩阵

每个实验写明设置、输出的图表和成立条件。种子默认是 3 个，指压缩者的采样种子；量化本身的校准抽样也跟着种子变。

### E1 动机：PPL 掩盖了工具调用和推理的损伤（A-P0）
- **设置**：27B 统一量化为 W8 / W4 / W3，每种都用 GPTQ 和 AWQ 各做一遍，测 KL/PPL 和全部 L3 主指标。
- **输出**：Figure 2 反差图。横轴是比特数；一条线是 PPL，几乎平坦；其余线是 BFCL 翻转率、BFCL 各类错误率和 MATH-500 / AIME 准确率，逐步恶化。另配 2–3 个具体的失败样例。
- **成立条件**：至少在 W3 下出现"PPL 变化 < 5%，但某项工具调用或推理指标显著恶化"。如果不出现，就去掉这张图，改用文献证据（Flat Score、Which Decisions）作动机。

### E2 单轮决策质量（A-P1，回答 RQ1）
- **设置**：16 GiB 和 12 GiB 两个预算。M_0 当压缩者，与下列基线对比，动作空间相同、评估次数对齐。
- **基线梯子**（借鉴 SEAL，从弱到强排列）：
  1. 随机合法配置（下界）；
  2. 统一 GPTQ / AWQ，取能放进预算的最大统一比特数；
  3. KL-ILP：用同一张 `profile_table` 和同一个求解器，只优化 KL；
  4. KL+行为 ILP：在 KL 上加固定权重的 `behavior_sensitivity`，权重在 dev 上网格选择，检验 LLM 是否只是学会了一个固定加权；
  5. EvoPress 式进化搜索（以整模型 KL 为目标）、随机搜索、CMA-ES，各评估 24 次；
  6. GAMMA，候选预量化的成本也要计入；
  7. 已发布的量化版本 GSQ-RCO；
  8. **本方法**：M_0 自压缩；
  9. 前沿 agent 上界：直接引用 CompressionBench Table 1，不重跑。
- **成本对齐**：两种口径都报，一是总评估次数，二是总 GPU 小时（包括 profile、失败执行和 agent 推理）。
- **输出**：Table 1 主表；Figure 3 是质量与包大小的 Pareto 图，按成本对齐。
- **成立条件**：本方法不差于 CMA-ES 和 GAMMA，或者质量相当但成本更低。明显更差时，先改诊断工具和反馈；还不行，就删掉"更优分配器"这条主张，论文主线保留在 RQ2。

### E3 递归的 2×2 拆解（A-P2，核心，回答 RQ2）

| | 每轮从 S 开始 | 在上一轮量化权重上继续压 |
|---|---|---|
| **冻结的 BF16 压缩者** | ① 非递归参照 | ② 测重复量化的损伤 |
| **当前的量化压缩者** | ③ 测压缩者退化的影响（**主设计**） | ④ 完整递归 |

- 四臂都按 16 → 12 → 10 GiB 跑；如果 10 GiB 还能通过，再加 8 GiB。
- **效应定义**（每个预算下、每个指标上分别计算）：
  - 预算效应：① 随预算的变化；
  - 重复量化效应 = ② − ①；
  - 压缩者退化效应 = ③ − ①；
  - 交互项 = ④ − ③ − ② + ①。
- **配对比较**：在每个固定的目标和预算下，BF16 压缩者和当前压缩者拿到相同的工具、历史和校准数据池，各自提出方案，然后执行，比较产物质量。这样可以在不跑完整递归的情况下直接测压缩者差异。
- **输出**：Figure 4 是四臂的能力和效率随代数的曲线，标出各自的自压缩深度 D；Table 2 是效应拆解，带 95% 置信区间。
- **成立条件**：不论压缩者退化效应是正、零还是负，都能写，前提是置信区间能把它和重复量化效应分开。

### E4 压缩者能力 E_t 随代数的变化（回答 RQ2）
- **设置**：M_0、M_1、M_2、M_3 各自完成固定的 12 GiB 自压缩任务（§2.2），3 个种子。
- **输出**：Figure 5（Figure 1 右下的放大版），E_t 随 k 变化，以冻结的 BF16 压缩者为参照线。
- **附加分析**：把 E_t 的下降和 M_t 在 BFCL、代码、指令遵循上的退化做相关分析，看压缩者退化通过哪种能力传导。

### E5 递归 vs 一步到位
- **设置**：M_0 直接一步压到最终预算（10 GiB 或 8 GiB），与递归得到的同预算产物比较。
- **回答的问题**：递归累积的损伤是否比单步压缩更大。2606.28438 缺这个对照，所以无法归因。

### E6 分析（回答 RQ3）
- **哪种能力先坏**：按数学、代码、闭卷知识、指令遵循、工具调用分别追踪逐代曲线（Figure 6）。
- **模型学会保护哪些模块**：画比特分配热力图（层 × 模块 × 代数，Figure 7），并与 When Reasoning Meets Compression 人工发现的"保护最后一层 MLP"对照。加一个**随机保护对照**：随机选同样数量的模块保持高比特。原论文缺这个对照。
- **压缩者行为**：每代的合法配置比例、调用了哪些工具、配置之间改动了多少；失败模式归类并命名，学 FT-Dojo 的命名方式。

## 10. 论文怎么写

### 10.1 叙事主线
**改进的对象和改进的执行者是同一个模型。改动它，也就改动了下一次改动的质量。**

借鉴 Self-Rewarding 的写法，同时看两条轴：一条是效率和能力，另一条是压缩者能力 E_t。不论结果是正是负，都有故事可讲；R-Zero 就专门开了一节讨论崩塌。

### 10.2 引言的写法
- **第一段（愿景）**：最强的模型最贵，推理成本是部署的主要负担。现有的 agent 压缩都依赖一个更强的外部压缩者，例如 CompressionBench、Self-Pruner、AutoQS。到了最前沿，谁来压缩最强的模型？
- **第二段（缺口）**：CompressionBench 在结论里把"压缩后的模型能否继续完成压缩"列为下一步，但没有做。
- **第三段（先用实验展示问题，借鉴 Self-MoE）**：A-P0 的反差图显示，PPL 几乎不变时，工具调用和推理能力已经受损。在自我压缩里，这种看不见的损伤会直接影响下一轮压缩，形成一个此前没人测过的反馈回路。
- **研究问题放进居中的方框**（借鉴 EvoGM）：*压缩一个模型，会怎样改变它继续压缩自己的能力？*
- **核心概念**：自压缩深度。

### 10.3 贡献（四条，分别对应问题、发现、方法、分析）
1. **问题与协议**：提出自量化闭环和固定外部评测协议，包括三层反馈、门槛相对第 0 代；定义自压缩深度和 E_t。
2. **核心发现**：用 2×2 设计把递归损伤拆成预算变紧、重复量化和压缩者退化三部分。
3. **决策质量**：同预算、同成本下，自压缩者与统一量化、GAMMA、CMA-ES 对比。如果输了，就如实报告，并改写成成本或泛化方面的结论。
4. **分析**：最先坏的是哪种能力；模型会自己学会保护哪些模块，并加随机保护对照。

### 10.4 章节结构（正文 9 页）

| 节 | 内容 | 页数 |
|---|---|---|
| 1 引言 | 上面的四段 + 研究问题方框 + 贡献 + Figure 1 | 1.5 |
| 2 相关工作 | agent 驱动的压缩；混合精度分配；压缩后的能力评测；递归自我改进 | 0.75 |
| 3 问题设定与协议 | 闭环、符号、E_t、自压缩深度、三层反馈、2×2 设计 | 1.5 |
| 4 PPL 掩盖了 agent 损伤 | E1，Figure 2 | 0.75 |
| 5 自压缩者能做出合理决策 | E2，Table 1、Figure 3 | 1.25 |
| 6 递归走多远、为什么停下 | E3、E4、E5，Figure 4、Figure 5、Table 2 | 2 |
| 7 模型保护什么、什么先坏 | E6，Figure 6、Figure 7 | 0.75 |
| 8 讨论、局限与未来工作 | 崩塌讨论；局限顺势引出下一篇 | 0.5 |
| 附录 | 完整配置空间、prompt、切分、每代 L3 全表、消融 E7、Gemma 和 Level 2 的结果、失败轨迹 | — |

实验各节的标题都用一句结论（借鉴 ACBench 和 R-Zero），节末放一个 Takeaway 框（借鉴 When Reasoning Meets Compression）。

### 10.5 Figure 1
- 左：递归闭环示意图（M_t 当压缩者 → 候选 → 固定的外部验收 → M_{t+1} 接任）；

### 10.6 结果分支

| 实际结果 | 论文的落点 |
|---|---|
| 递归稳定，压缩者退化效应接近 0 | "模型可以在没有监督者的情况下让自己更便宜，自压缩深度为 X" |
| 递归崩塌，压缩者退化效应显著为负 | "压缩侵蚀了压缩所需的能力，最先坏的是'要不要调用工具'"，加上 2×2 的机制归因 |
| 自压缩者输给 GAMMA | 删掉贡献 3，主线保留在递归发现上 |
| 重复量化效应远大于压缩者退化 | "瓶颈在权重，不在压缩者"，这是对 RSI 讨论的一个具体修正 |

### 10.7 局限与未来工作
激活量化、MoE、代码级压缩；以及"把压缩后的恢复交给模型自己做"，例如 SDFT 式的自蒸馏 LoRA，正好接到 Paper B。

### 10.8 要避免的写法
- 声称"首次 agent 压缩"或"首次接任"；
- 只报 PPL 或总分（LLM-KICK、Flat Score 的教训）；
- 只用单个种子。
