## 研究问题
RLVR "zero" 设置虽然不需要 CoT 标注，但仍然需要人工整理的问题–答案集合。作者问：能否让一个模型自己提出任务、自己解题、只依靠环境（代码执行器）给出可验证反馈，在完全不用外部数据的情况下提升推理能力？

## 方法细节
- **模型**：主实验 Qwen2.5-7B（base）与 Qwen2.5-7B-Coder；扩展实验 Qwen2.5-Coder-3B、Qwen2.5-Coder-14B、Qwen2.5-14B、Llama-3.1-8B。均从**预训练 base 模型**直接开始（无 SFT）。
- **单一模型、双角色**：同一个参数化策略 π_θ 同时扮演 proposer 和 solver（p.4 第 3.1 节；算法 1 p.7）。两种角色共享同一组权重、同一个 checkpoint，在每一步联合更新。
- **谁出题**：同一模型（proposer 角色）。以任务类型（演绎 / 溯因 / 归纳）和从 buffer 中采样的 K=6 条历史自生成三元组为条件，生成 (程序, 输入) 或给定程序生成多组输入+自然语言描述。
- **谁验证 / 给奖励**：
  - **外部 Python 代码执行器**负责构造 gold 答案（执行程序得到输出）、过滤任务（语法、安全模块黑名单、确定性检查——跑 2 次比较）、验证 solver 答案（值相等）。这是一个非学习的外部验证器。
  - proposer 的"可学习性"奖励由**同一模型**在 solver 角色下做 N=8 次 Monte Carlo rollout 估计成功率 r̄，奖励 = 1−r̄（r̄=0 时为 0）（式 4，p.5）。
  - solver 奖励为二值正确性（式 5），外加格式惩罚（式 6）。
- **谁决定超参/训练方案/写训练代码**：**全部由人类研究者固定**（表 3，p.23：lr 1e-6、AdamW、batch 64×6、500 steps、TRR++、无 KL 等），"所有 run 都不改"。模型不参与任何超参、训练配置或训练代码的决策。
- **更新方式**：在线 RL，Task-Relative REINFORCE++（TRR++）——对 3 任务 × 2 角色共 6 种配置分别做奖励归一化基线（式 8，p.8），PPO 目标，无 KL。论文未提 LoRA；基于 veRL，A800 集群，每个实验 3–5 天。【推断】为全参数更新（文中无任何 LoRA/PEFT 字样，grep 验证）。
- **轮次 / 递归**：不是离散"轮"，而是**逐步在线自博弈**：每一步都由当前权重提出任务、再由当前权重解题、联合更新；更新后的模型在下一步立即成为新的 proposer。总训练 500 步（表 3），图中展示到约 250–280 步。buffer 初始化时只用一个恒等函数三元组作为种子（图 5），然后由 base 模型自生成种子集（无模型更新）。
- **外部更大模型**：训练环路中**没有**更大的外部 LLM；唯一外部组件是 Python 执行器。评测用 greedy decoding 的规则式打分，未见 LLM 评审。

## 关键实验与数字
- **表 1（p.9）主结果，7B**：AZR-Base 总 AVG 46.8（+7.0 相对 Qwen2.5-7B 39.8），MAvg 38.4（+10.9）；AZR-Coder AVG 50.4（+10.2），CAvg 61.6（+5.0），MAvg 39.1（+15.2）。作者称 AZR-Coder 比此前最佳 zero 模型（ORZ 48.6 等）总平均高 1.8 点。注意 AZR-Base 在 HumanEval+ 上 −1.9。
- **图 6b / 表 5（p.10, p.34）规模**：Coder 3B/7B/14B 总平均增益 +5.7/+10.2/+13.2；Qwen2.5-14B-Base 也有大幅数学增益（如 AIME'25 3.3→20.0），但 HumanEval+ 78.0→70.7 下降。Llama-3.1-8B 只 +3.2，弱于 SimpleRL-Zoo（+4.5）。
- **表 2（p.12）消融（7B base）**：只用演绎 43.3；去掉归纳 43.8；去掉 K 条参考条件 43.8（数学 −5）；**只训 solver、proposer 不训** 45.4；完整 46.8。即 proposer 训练带来 1.4 点总平均增益。
- **图 8（p.12）pass@k**：k 到 512 时 5 个 benchmark 中 4 个不低于 base（AIME24 k=512 例外）。
- **图 6a / 图 16（p.10, p.25）ID 曲线**：7B、14B 在 200 步后仍在上升，3B 趋于平台期。
- **饱和/崩塌**：正文和附录未报告 AZR 本身的性能崩塌；3B 显示平台期。附录 D.3 提到尝试"按新近程度采样参考代码"时观察到"潜在崩塌"（p.51），但无数字。OOD 曲线（图 30–33）只展示到约 250 步，提取文本无法读出是否有后期下降。
- **附录 C.4（p.34–35，图 29）**：程序复杂度（ComplexiPy、Halstead）与多样性（AST 编辑距离、答案多样性）随训练上升，虽未直接纳入奖励。
- **附录 D（p.51–52）失败尝试**：错误类型推断任务、复合函数课程（模型学会 f(g(x))=g(x) 的捷径）、用 LeetCode 初始化种子（代码初期高、最终持平、数学更低）、复杂度/多样性额外奖励（无显著差异）、去注释/去全局变量（性能下降）。

## 作者自己声明的局限
- 未解决如何安全管理这种自我改进系统；Llama-3.1-8B 出现令人担忧的 CoT（"uh-oh moment"，图 34），仍需人类监督（p.14）。
- 只考虑确定性程序，随机程序留待未来（p.8）。
- proposer 仍有提升空间（任务干扰、覆盖激励）（p.12）。
- 学习进度估计、p(z) 初始化/更新策略、环境 f 的设计都待研究（p.14、D.3）。

## 方法问题与替代解释
- 【推断】增益很大一部分可能来自"激活"Qwen2.5 已有的数学/代码能力（已有工作表明 Qwen2.5 对很弱的 RL 信号也敏感），而非自博弈课程本身；"只训 solver"的消融（45.4）已拿到大部分增益（相对 base 39.8 为 +5.6，完整方法 +7.0），说明 proposer 的学习只贡献了较小一部分。
- 【推断】可验证性完全依赖外部 Python 执行器；离开代码域（无 oracle）时机制不能直接迁移——这正是 R-Zero 批评的点。
- 【猜测】Llama-3.1-8B 增益弱且低于 SimpleRL，可能说明方法依赖 base 模型的代码先验强度，作者也承认增益随 base 能力缩放。
- 所有评测 greedy 单次运行，无方差报告；AIME 题量极小（30 题），+13.3 这类数字对应 4 道题，噪声大。【推断】
- 训练超参在所有 run 中固定，未做敏感性分析。

## 与 core claims（B1–B4）的关系
- **B1（同一 checkpoint 编写自己的适配：生成训练数据 + 决定如何更新自己，或直接生成适配器权重）**：**部分覆盖**。同一 checkpoint 生成训练任务（且任务的难度/可学习性由同一模型评估），这覆盖了"自己生成训练数据"。但模型**不**决定超参、LoRA 配置、训练代码或更新方案——这些全部由人类固定（表 3）；也不生成适配器权重。"如何更新"的部分未覆盖。
- **B2（适配器作用于同一模型提升下游任务）**：**部分覆盖**。更新作用于同一模型并提升下游（OOD 数学/代码）性能；但更新方式是 RL 全参数（【推断】），**无 LoRA/适配器**。
- **B3（递归：被适配模型成为下一轮编辑者，编辑能力与任务性能共同提升）**：**部分覆盖**。逐步在线递归：更新后的同一权重立即作为下一步的 proposer；作者显示 proposer 训练有益（表 2）、提出的任务复杂度随训练上升（图 29）。但"编辑能力"在此仅指"出题能力"，不包括决定训练配置；也没有离散多轮、每轮产出一个适配器的结构。
- **B4（无更大/更强外部模型参与数据生成、决策或评判）**：**覆盖**。环路中无外部 LLM；唯一外部组件是非学习的 Python 代码执行器（作为验证器/环境），这一点需在比较中注明。
