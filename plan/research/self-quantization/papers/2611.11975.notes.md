## 研究问题
在固定权重比特宽度（如 W4）的前提下，用 LLM 驱动的“提议-评估”迭代搜索，为每层、每类算子分配不同的 GPTQ group size。难点在于：真实量化加评测很贵，便宜的代理指标又不一定能反映量化后模型的真实表现。作者要回答的是：在有限的真实量化评估预算下，LLM 搜索怎样把提议变成合法策略，并借助少量真实评估不断改进（p.2, Sec.1）。

## 方法细节
- **提出策略的 LLM 和被量化的模型是不是同一个**：不是。默认的 proposer 是 **Qwen-Plus**（闭源 API，p.8 Sec.4.1；Table 3 p.14），另外做过一次 **DeepSeek** proposer 的对照（Table 8 p.16）。被量化的是 Qwen2.5-7B、Qwen2.5-7B-Instruct、LLaMA-7B、Llama2-7B，迁移实验还用了 Vicuna-7B-v1.5（p.7 Sec.4.1）。proposer 和被量化模型完全是两个模型，没有任何“自己量化自己”的设定。
- **动作空间**（Sec.3.1 p.4–5，Eq.1）：
  - 比特宽度在一次搜索中固定，**不是搜索变量**。W2/W3/W4 各自独立跑一次搜索（Table 7）。
  - 每层有 4 个决策组：QKV、Out、GateUp、Down。每个组从 G={−1,16,32,64,128} 里选 group size；−1 是实现里的特殊分组选项【推断：在 GPTQ 实现中通常指 per-channel，不分组】。Qwen2.5-7B 共 196 个模块，搜索空间约 5^196（附录 E.1 p.19）。
  - 量化器固定为 GPTQ。**不搜索**量化器、校准数据、比特宽度，也不做剪枝。
  - LLM 每次输出 1–4 个稀疏的层级 SEARCH/REPLACE 编辑块，改动父策略（Sec.3.2 p.5）。改完后做合法性校验，用规范化哈希去重，若重复则做确定性的 novelty repair。作者明确说没有独立的局部搜索算子。
  - 敏感度统计只作为 Stage-1 的辅助信号，**没有**作为显式的逐层指令交给 LLM（p.5）。
- **代理指标与真实评估**：
  - Stage-1 便宜代理：NLL 退化、跨领域统计、敏感度信号、存储估计，合成一个标量 cheap proxy score（Eq.2–3，p.5）。
  - 真实（physical）评估：每 K=5 次迭代，取当前窗口里最后一个合格候选，用 GPTQ 实际量化，在 ARC-C、PIQA、BoolQ 上评测，取平均作为 Macro3，并测 checkpoint 字节数（Sec.3.4 p.6–7，Eq.4–5）。选哪个做真实评估**不按代理分数排序**，只按时间顺序取。
  - 搜索结束后，用 7 个任务的 Macro7 做最终评测，不回传到搜索。但其中 3 个任务和 Macro3 重叠，作者也承认 Macro7 不算完全 held-out（p.8；附录 A.1 p.13）。
- **搜索预算**：T=100 次迭代，最多 20 次真实量化评估（Table 3 p.14）。LLM token 数和 API 成本**没有保留记录**（附录 A.4）。硬件为单张 RTX 3090 24GB，batch size 1。
- **是否多轮、被量化模型后来是否当 proposer**：搜索本身是 100 次迭代的多轮循环，但 proposer 始终是外部的 Qwen-Plus。被量化的 7B 模型从不参与提议，**没有递归**。

## 数据集与评测
- 搜索期（Macro3）：ARC-Challenge、PIQA、BoolQ。
- 搜索后（Macro7）：MMLU、HellaSwag、ARC-E、ARC-C、PIQA、WinoGrande、BoolQ，沿用 FBQuant 的评测套件。
- 指标是准确率平均和 checkpoint 字节数。但正文和附录**没有任何表格报告 AutoQS 与 G128 基线的实测存储对比**【推断：存储只在方法部分提到被测量】。
- **没有测推理速度或延迟**：作者明确说 runtime latency 不是评估目标（p.7 第 429–430 行附近）。也没有测显存占用、吞吐。
- **没有测 agent 或工具调用能力**，全部是多选、常识类 benchmark。

## 关键实验与数字
- **Table 1（p.8）**，Qwen2.5-7B base，W4：AutoQS Macro7 为 74.21，FP16 为 74.25，最强外部基线 SVDQuant 为 73.85，GPTQ G128 为 72.09，AWQ 为 73.15。外部基线数字**直接抄自 FBQuant 的 Table 8**，不是在同一套评测管线下重跑的。ARC-C 上 AutoQS 是 56.57，比 FP16 的 51.02 还高 5.5 分。
- **Table 4（p.14）**，Qwen2.5-7B-Instruct：AutoQS 75.16，GPTQ G128 74.46（+0.70），AWQ 74.04（+1.12），FP16 75.12。摘要里的 0.70 / 1.12 就来自这张表。ARC-C 上 AutoQS 57.94，FP16 55.03。
- **Table 2（p.8）**，同种子消融（种子 1234，Qwen2.5-7B W4），这是和非 LLM 搜索唯一的对比：
  - Full（Qwen-Plus + 反馈）：最佳 Macro3 为 73.8521，出现在第 100 次迭代。
  - No-feedback：最佳 Macro3 为 72.5777，出现在第 45 次迭代。
  - Random proposer（带种子的合法随机变异，其余流程相同，预算同为 100 次迭代、20 次真实评估）：最佳 Macro3 为 73.4465，出现在第 15 次迭代。
  - 结论：LLM 比随机变异只高约 0.41 个 Macro3 点，而且只跑了一个种子。**没有**与进化算法、贝叶斯优化、HAQ/HAWQ 式敏感度分配，或其他经典非 LLM 方法在同预算下比较，也没有报告 Random proposer 的 Macro7。
- **Table 8（p.16）**，proposer 与种子：Qwen-Plus 种子 2026 得 73.27，种子 1234 得 74.21，DeepSeek 种子 1234 得 73.69。种子间差了 0.94，比 AutoQS 相对 GPTQ 的增益（0.70）还大。
- **Table 7（p.16）**，比特宽度：W2 为 36.22（接近随机），W3 为 63.79，W4 为 74.21。
- **附录 C.3 与 Table 10（p.16, p.18）**，LLaMA-7B 的 8 个候选：Macro3 与 Macro7 的 Pearson r=0.135，Spearman ρ=0.071。搜索期排第 1 的候选，Macro7 只排第 6。
- **Table 9（p.17）**，同一轨迹的中间 checkpoint：Macro7 在 73.55–74.21 之间波动，不是单调上升。
- **Table 5 / 6（p.15）**，零样本迁移：LLaMA-7B 上搜出的策略直接用到 Llama2-7B，得 64.56，uniform G128 为 64.49；用到 Vicuna 得 65.95，uniform 为 66.10。
- **Table 11（p.18）**：Full 策略中 28.57% 的模块不是 G128；Random 策略只有 10.20%。

## 作者自己声明的局限
- 外部基线固定用 G128，只代表表中报告的那些配置（E.3 p.20）。
- 没有量化节省的人工时间，宣称的优势是“自动化”，而不是机器时间上的加速（E.2–E.3）。
- Qwen2.5-7B-Instruct 的策略产物没能找回，所以没有做结构分析（E.3）。
- token 和 API 成本没有记录（A.4）。
- Macro7 不完全 held-out（A.1）。Macro3 与 Macro7 相关性很低，样本也太少（C.3）。
- 窗口内没有合格候选时就终止，作者说这条规则还需要和实际执行的控制器核对（Sec.3.4 p.7）。
- 不评估延迟（Sec.3.4）。

## 方法问题与替代解释
- 【推断】增益很可能主要来自 group size 变小带来的额外元数据，也就是每个权重实际占用的比特数变多了，而不是“分配更聪明”。论文虽然测了 checkpoint 字节数，但正文和附录都没有报告 AutoQS 与 G128 的存储对比，所以并不是同存储预算下的比较。与之对比，Random 策略更接近全 G128（G128 占 89.8%），分数也更低，这和“更多小 group 就更好”的解释是一致的。
- 【推断】ARC-C 比 FP16 高 5.5（base）和 2.9（Instruct），而 ARC-C 正好在搜索目标 Macro3 里，说明存在对搜索期任务的选择偏差或过拟合。另外 4 个未参与搜索的任务（MMLU、HellaSwag、ARC-E、WinoGrande）上，AutoQS 在 Table 1 和 Table 4 里都不如 FP16，也不如部分基线。
- 【推断】种子方差（0.94）大于相对基线的增益（0.70），而“LLM 优于随机”只有一个种子、Macro3 差 0.41。统计证据偏弱。
- 【推断】Table 1 的外部基线是从其他论文抄来的，与本文自己测的 FP16 不同源，跨管线比较不严格。
- 【猜测】正文里有几处像草稿的措辞（例如“supplied protocol”，以及终止规则还需与控制器核对），Table 7 的标题里还混入了与主题无关的自引。这些说明稿件成熟度有限。

## 与 Topic A 核心主张的关系
- **A1（同一 checkpoint 为自己的权重做决定并执行）**：**未覆盖**。proposer 是外部的 Qwen-Plus 或 DeepSeek API，被量化的是 7B 开源模型，两者不同。决策只涉及 group size，不涉及比特、量化器、校准数据。执行由固定流水线（GPTQ）完成，不是 LLM 通过工具调用来执行。
- **A2（递归：量化后的模型担任下一轮 editor）**：**未覆盖**。有 100 次迭代的搜索循环，但量化产物从不担任 proposer，也没有研究 editor 退化的影响。
- **A3（真实推理效率加能力保持，含 agent 和工具调用，由外部固定评测判定）**：**部分且很弱**。效率只看 checkpoint 存储，而且没有报告对比数字。明确不测延迟，也不测显存和吞吐。能力只评多选常识类 benchmark，没有 agent 或工具调用评测。有固定的外部 Macro7，但与搜索目标部分重叠。
- **A4（LLM 推理提出的分配在同预算下优于或持平经典非 LLM 分配）**：**部分覆盖，是最接近的一点**。论文让 LLM 提出分配，并在同迭代预算、同种子下与“合法随机变异”比较（Table 2，Macro3 为 73.85 对 73.45），与 uniform G128 的 GPTQ/AWQ 比较时略占优。但它没有和进化、贝叶斯、HAWQ/HAQ 这类经典分配方法比较，没有做同存储预算的比较，只有单种子，搜索变量也只有 group size，不涉及比特分配。
