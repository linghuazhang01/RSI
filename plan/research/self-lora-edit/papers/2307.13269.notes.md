## 研究问题
多个 LoRA 各自在上游任务上训练好以后，面对一个没见过的新任务、只有约 5 个带标签样例时，能否不用梯度、不加参数，只靠给已有 LoRA 配一组标量系数再组合，就适配这个新任务？目标是让性能接近 ICL，同时推理 token 数与 zero-shot 相同（p1–2，第 89–103 行）。

## 方法细节
- **被组合的对象**：LoRA 模块，不合并全模型。底座 FLAN-T5-large（主实验），附录另有 T5-large 和 FLAN-T5-xl。候选池是在约 200 个 FLAN 任务上分别训练的 LoRA（rank 16，batch 64，lr 1e-4，10 epoch；p21 附录 G 第 1376–1385 行）。每次实验从池中**随机抽 20 个**作为候选（p5 第 317–319 行）。
- **组合方式（COMPOSE）**：按元素线性组合，公式 (1) 为 m̂ = (Σ wᵢAᵢ)(Σ wᵢBᵢ)，也就是 A、B 两个因子分别加权求和后再相乘，并不是对 ΔW=AB 加权求和（p4 第 254 行）。所有模块的 rank 必须一致。
- **搜索空间**：每个 LoRA 只有 **1 个全局标量 wᵢ**，所有层共用，**不分层**，可以取负。N=20 时就是 20 维。约束 |wᵢ| ≤ 1.5，初始化全 0（p21 第 1378–1380 行）。
- **目标函数**：在 5 个少样本上算交叉熵损失，加 L1 正则 α·Σ|wᵢ|，α=0.05（p4 第 273–277 行，p21 第 1383 行）。
- **优化器（ADAPT）**：无梯度黑盒优化，用 Nevergrad 的 Shiwa 元优化器，大多数设置下实际选中 **CMA-ES**（p5 第 289–299 行）。预算是**最大迭代 K=40**（p21 第 1381 行；正文 p7 第 443 行说"40 steps"）。
  -【推断】论文没有说清"40 次迭代"是指 40 次函数评估，还是 40 代 CMA-ES（每代多个个体）。Nevergrad 里的 budget 通常就是函数评估次数，所以很可能一共只评估约 40 个候选，每个候选在 5 个样本上前向一次。
- **有没有 LLM 参与决策**：没有。系数完全由 CMA-ES 根据损失搜索。LLM 只被当作打分用的推理器，不会诊断，也不写代码。
- **校准数据量**：每个任务 5 个带标签样例，和 ICL 用的是同一批（p21 第 1381–1382 行）。每个任务跑 3 次，每次换一组 5-shot。
- **成本**：作者称在单张 A100 上不到 1 分钟（p2 第 119–120 行），显存约 5GB，LoRA 微调约 34GB，全量微调约 40GB（p8 第 538–542 行）。

## 数据集、评测、模型规模
- 评测：BBH 的 27 个任务，指标为 Exact Match（p5 第 321–325 行）。
- 模型：FLAN-T5-large（约 780M），附录 D 用 FLAN-T5-xl（约 3B），附录 C 用 T5-large（非指令微调）。【推断】都是 encoder-decoder 小模型，没有 decoder-only LLM 的实验。

## 关键实验与数字
- **Table 1（p6，第 357–408 行）**，FLAN-T5-large 上 BBH 27 个任务的平均：Zero 27.0；ICL 37.3；IA3 31.6；LoRA 37.7；FFT 42.1；**LoraHub 34.7**（第 406 行）。平均每个样例的 token 数：ICL 597.8，其余都是 111.6（第 407 行）。
  - LoraHub **低于**在同样 5 个样本上直接训练 LoRA（37.7 对 34.7），也低于 ICL。作者承认它仍落后于 LoRA 微调和 FFT，在 Dyck Languages 这类和上游任务差异大的任务上尤其明显（p6–7，第 421–436 行）。
  - 梯度基线的训练方式：在同样的 3 组 5-shot 上训练 40 epoch，取训练结束时的 checkpoint，不做模型选择（p5 第 331–335 行）。
- **Table 4（p16，附录 B）** 报告 3 次运行中的最好结果：ICL 38.4，IA3 32.1，LoRA 40.9，FFT 46.2，LoraHub 41.2（第 1063 行）。正文说 best 设置下 LoraHub 在 18 个任务上超过 ICL（p6 第 415–416 行）。【推断】"best"是事后看测试集挑出来的上界，相当于 oracle 选择，不能当作公平比较。
- **Table 2（p7，第 466–479 行）**：LoRA 检索基线（按 5-shot 损失挑出最好的单个 LoRA）31.7；LoraHub avg 34.7；LoraHub best 41.2。这是论文里唯一的"非组合"选择基线。
- **WTQ 合成实验（p7–8，附录 A p15）**：把专门在 WTQ 上训练的 LoRA 放进候选池，CMA-ES 给它的权重最高，组合后的模块比单独用 WTQ LoRA 略好一点（文中没给具体数字）。
- **Table 3 / Table 8（p15、p20）**：平均权重排前 5 的模块（WIQA、RACE 等）单独使用时，在 BBH 上只比 zero-shot 高 -1.86 到 +3.78（第 1321 行）。
- **Table 5（p17，附录 C）**：T5-large 上 rank 4/16/64 的平均分为 16.14 / 20.78 / 14.76，rank 16 最好。
- **Table 6（p18，附录 D）**：FLAN-T5-xl 上 Zero 25.8，LoraHub avg 36.5（5 个种子），best 41.3。
- **Table 7（p19，附录 E）**：先按 5-shot 损失预筛出 20 个候选，平均分从 34.7 升到 35.4。
- **Figure 3 / 附录 H（p21）**：候选 LoRA 越多，方差越大，最好成绩也越高。作者认为方差主要来自候选集合的选择，与优化器的随机种子关系不大（第 1388–1394 行）。
- **Table 9 / 附录 I（p22）**：去掉 |w|≤1.5 的约束后平均分从 34.7 降到 33.5。
- **没有做的基线**：所有候选**简单平均**（w=1/N）、随机搜索、TIES/DARE、逐层系数，全都没有比较。

## 作者自己承认的局限
- 性能不如 ICL，也不如 LoRA 微调和 FFT，在和上游差异大的任务上更差（p6–7）。
- ADAPT 阶段要额外推理，对一次性任务来说 ICL 更划算（p7 第 440–452 行）。
- 同时组合的模块太多会让搜索空间急剧变大、学习过程不稳定，所以只能随机剪枝候选（p4 第 256–260 行）；候选集合是方差的主要来源（附录 H）。
- 原文没有单独的 Limitations 小节，以上都是从 Discussion 和附录里整理的。

## 方法问题与替代解释
-【推断】公式 (1) 是 (ΣwA)(ΣwB)，展开后有 wᵢwⱼAᵢBⱼ 交叉项。各 LoRA 是独立训练的，Aᵢ 和 Bⱼ 的基不对齐，交叉项基本是噪声。这种组合并不等于对 ΔW 做线性 task arithmetic。如果复现时改成 Σ wᵢAᵢBᵢ，结果可能不同。
-【推断】只有 5 个样本，损失又是交叉熵，40 次评估很容易过拟合到这 5 个样本。正文结果是 3 次运行的平均，没有单独的 dev 选择，所以论文里没有"dev/test 分离"这一层。
-【推断】LoraHub 的平均分比检索单个 LoRA 高 3 分，但也可能来自"多个 LoRA 叠加带来的泛化格式偏置"（比如输出格式被纠正了），不一定是真的组合了技能。论文没有做简单平均的对照来排除这种可能。
-【猜测】BBH 各任务的 EM 本来就很低、方差很大（比如 Dyck、Word Sorting 接近 0），平均分差几个点在统计上未必显著，论文没有报告置信区间。

## 与 core claims（C1–C4）的关系
- **C1（同一模型通过代码自编辑自己的 LoRA）**：**未覆盖**。LoraHub 用固定的 CMA-ES 算法搜索系数，LLM 不参与诊断，也不写代码。组合的是"别人在别的任务上训练的 LoRA"，不是被编辑模型自己刚训练好的那个 adapter。属于"固定算法做编辑"，恰好是 C1 明确要区别的对象。
- **C2（同等评估预算下胜过非 LLM 搜索）**：LoraHub 本身就是 C2 点名要比的"LoraHub-style 系数优化"基线。它和 C2 的关系是提供基线，不是覆盖 C2。论文自己比过的只有 zero-shot、ICL、IA3、LoRA、FFT 和单 LoRA 检索，没有比 TIES/DARE、简单平均、随机搜索，也没有任何 LLM 写的编辑。
- **C3（递归、编辑者能力 E_t）**：**未覆盖**。一次性组合，部署后不再更新（p3 第 200–201 行），没有递归，也没有编辑者这个角色。
- **C4（持续多任务、遗忘控制、无外部强模型、固定外部评测）**：**基本未覆盖**。它的设定是跨任务泛化到新任务，不是持续学习，没有测遗忘，也没有逐轮的 adapter 栈。"不依赖外部强模型"这一点满足（纯数值优化）。评测时 5 个样本既用于优化，又不单独留 dev2，测试集是 BBH 测试部分。

## 作为 C2 中"非 LLM 搜索基线"的复现建议
- **算法**：Nevergrad `NGOpt`/`Shiwa`，或直接用 `CMA`。对 K 个候选 LoRA 各配一个全局标量 wᵢ，初始化 0，边界 [-1.5, 1.5]，目标是 dev 上的交叉熵损失加 0.05·Σ|wᵢ|。
- **组合方式**：为了忠实于原文，可以按原公式 (ΣwA)(ΣwB) 实现，同时再跑一个 Σwᵢ·(AᵢBᵢ) 变体（【推断】按公式 (1)，实现上应是分别对 lora_A、lora_B 加权求和；未核对官方代码 github.com/sail-sg/lorahub）。在 B' 的设定里，候选应包括"本轮原始 LoRA + 之前的 adapters + 训练轨迹上的 checkpoint"，搜索对象是这些候选的系数。
- **预算**：原文是 40 次迭代、5 个样本。C2 要求等评估预算，建议把 Nevergrad 的 budget 设成与 LLM 编辑者相同的候选评估次数（例如 LLM 一共提出 N 个候选，就给 CMA-ES N 次评估），目标在同一个 dev 集上算；最终用同样的 dev2 做接受、sealed test 做报告。
- **建议加的扩展**：逐层系数版（K×L 维，对 CMA-ES 更难，可作为"更强的 LoraHub"），以及简单平均和随机搜索两个对照，因为原论文没有报告这两项。
- **超参**：L1 α=0.05，|w|≤1.5，rank 一致（原文 16），候选数原文是 20。
