## 2. 做的是什么决策
HAQA **不做逐层/逐模块的混合精度分配**。它决定三类东西：
1. **量化模型的微调超参**（QAT/QLoRA）：ResNet 用 DoReFa QAT，调 lr、batch、weight decay、momentum、epochs；LLaMA 用 QLoRA，调 lr、per-device batch、grad accumulation、weight decay、max_steps、max_grad_norm、lora_r/alpha/dropout、warmup_ratio（p.13–14 App. C；p.16 prompt）。量化比特本身在微调实验里是**外部固定的**（w8a8/w4a4/w2a2 或 INT4/INT8），不归 agent 决定。
2. **部署时的全局量化类型**：在 FP16/INT8/INT4 中整模型选一个，满足显存上限（Table 5，p.8；App. E，p.19）。粒度是整模型。
3. **llama.cpp CUDA kernel 的执行配置**（逐 kernel）：gridDim/blockDim、tiling、unroll、内存层级、线程调度，必要时**直接改 kernel 代码**（p.4、p.16–17）。

被量化的模型：CNN（ResNet20/32 on CIFAR-10，ResNet50 on ImageNet）和 LLM（LLaMA2-7B/13B、LLaMA3.2-3B、LLaMA3-8B；移动端 openllama-3B、tinyllama-1.1B、gpt2-large）（p.6）。

## 3. 驱动决策的信息（LLM 看到什么）
决策者：**GPT-4-0613**（p.6 "ChatGPT-4 ... GPT-4-0613 as agent"）。没有工具调用，只有多轮对话。

**Prompt 结构**（p.4 §3.1；p.14–19 App. D/E 的完整样例）：
- system 消息：一句角色设定（"expert assistant specialized in optimizing hyperparameters"）。
- **静态 prompt**（user 消息，整个优化过程不变）：
  - (a) 硬件规格：用一个 JSON 片段写架构、CUDA/Tensor core 数、FP16/INT8/INT4 峰值算力（A6000 样例 p.16）；移动端样例写明 INT4 "Not Supported Natively (Emulated via INT8)"（p.19）。
  - (b) 部署目标：显存上限（如 10GB），要求"选一个满足显存、性能更好的位宽"；逐 kernel 信息以 JSON 给出：kernel 名、张量类型、src/输出 shape、默认 gridDim/blockDim、unroll size、kernel 源码（p.17）。
  - (c) 微调目标：数据集、搜索空间（每个超参写类型 UniformFloat/UniformInteger、范围、默认值、是否 log 尺度）、量化方法核心代码、模型结构代码、微调代码（论文中以 "xxx" 省略）（p.14–16）。
  - 行为指令：每轮只给一组配置；首轮用默认值；超参必须在范围内；loss 不变就换区域探索；输出 JSON（给出 JSON 模板）。
  - **ReAct 段落**（紫色字）：要求先写 Thought、再 Action、再根据 Observation 调整，并"review the history"（p.14、p.17）。
- **动态 prompt**（每轮追加一条 user 消息，p.15–18）：
  - "剩余 N 轮"提示（如 "there are 7 rounds left"）；
  - 当前配置（JSON）；
  - 结果：ResNet 为验证精度 + 每 epoch 平均训练 loss 列表；LLaMA 为 lm-eval 原始结果字典（每任务 acc、acc_stderr、acc_norm 等）；
  - 部署：当前 kernel 执行配置 JSON + 测得的延迟（如 "Latency: 0.619 us"）。
- **历史/记忆**：整个对话历史（之前的 user 结果 + assistant 推理与配置）都保留在上下文中；用户可设定历史长度上限，以免超过上下文窗口导致中断（p.5 §3.3）。没有外部记忆或检索。

**完全没有给 LLM 的东西**：逐层/逐模块的敏感度、权重/激活统计、Hessian、量化误差、per-layer 延迟剖析。唯一的"诊断"是端到端精度/loss 曲线、整 kernel 延迟、以及静态硬件规格表。

成本（App. B p.13）：每次 API 调用平均 2.34 s；2–3 个模型端到端优化约 150K tokens、约 $5。但**每轮的真正成本是一次完整的 QAT/QLoRA 微调 + 评测 + 部署测速**，论文未报告这部分的 GPU 时间。

## 4. 决策过程
LLM-in-the-loop 的黑盒超参优化（类似 AgentHPO/OPRO）：LLM 输出配置 → 运行微调与部署 → 精度/延迟写进动态 prompt → LLM 再输出，直到达标或用完迭代上限（p.4 §3.2）。**每个实验最多 10 轮**，所有实验一致（p.7 "maximum of 10 tuning rounds"）。显存约束下选位宽靠 LLM 自己"计算显存需求"（p.8，如 13B INT8 需 13GB，12GB 则拒绝）。动作空间：微调超参 JSON；部署为 `{griddim, blockdim, tiling size, code changed, code}` JSON（p.17）；位宽为自然语言回答（p.19）。

## 5. 关键结果
- Table 1（p.6，ResNet DoReFa QAT，均值±std）：HAQA 在所有 9 个设置上最高。例如 ResNet20 w4a4：HAQA 88.38 vs Human 87.17、Local 82.88、BO 82.29、Random 82.16、NSGA2 81.65；Default 81.15。w2a2 时 Default 不收敛（"––"）。
- Table 2（p.7，QLoRA LLaMA，8 个下游任务）：HAQA AVG 均最高，如 LLaMA2-7B INT4 63.11 vs Human 62.04 / Local 61.99 / Bayesian 61.49 / Random 61.29 / NSGA2 60.79；LLaMA3-8B INT4 67.87 vs Local 66.75。Table 6（p.13）是带 std 的同一组数。
- Fig. 4（p.7）：LLaMA3.2-3B INT4 上收敛曲线，作者称 HAQA 收敛更快更稳（图内容未抽取到）。
- Table 3（p.8）：kernel 级延迟加速 1.07×–2.31×（SiLU [11008,64,1] 10.44→4.51 µs，2.31×；MatMul 1.35–1.63×）。
- Fig. 5（p.8–9）：端到端 token 生成相对 llama.cpp 默认约 1.2–1.5×。摘要中的 "2.3×" 实际来自单个 kernel（SiLU），不是端到端。
- Table 5（p.8）：LLaMA2-13B 在 4/12/20/28GB 下的可行位宽选择。
- Table 4（p.8）：OnePlus 11 上 INT8 吞吐略高于 INT4（openllama-3B 5.25 vs 4.95 tok/s）。

## 6. 隔离各信号价值的消融
- **没有任何消融**：没有去掉 ReAct、去掉历史、去掉训练 loss 曲线、去掉硬件规格、去掉代码上下文、换 LLM 的实验。全文 grep "ablat" 无结果。
- ReAct 的作用只是定性描述：用来修正三类问题（格式不符、违反约束、无关内容），声称"curtails blind exploration"，但没有数字（p.5）。
- 与非 LLM 基线比较：Local search、Bayesian optimization、Random search、NSGA2、Human、Default（Table 1/2/6）。HAQA 限 10 轮；**论文没有明确说基线也用 10 次评估**（Fig. 4 收敛曲线暗示同横轴，【推断】可能是同预算）。BO/NSGA2 在 10 次评估下几乎不可能发挥，这种比较本身对 BO 不利【推断】。
- 部署侧只对比 llama.cpp 默认配置，没有和 TVM/Ansor 等自动调优器或随机搜索在同预算下比较。

## 7. 可加性/交互的证据
无。论文声称 agent "jointly tunes all settings for synergistic optimization"（图 1 说明，p.2），但没有实验比较联合调参与逐个调参。

## 8. 作者声明的局限 / 观察到的失败模式
- 未单列局限章节。
- 报告的失败模式（p.4–5）：(1) 回复不符合要求格式；(2) 配置违反预设约束（超出范围）；(3) 回复包含与任务无关的内容。用 ReAct prompt 缓解，无频率统计。

## 9. 批判
- **"反直觉发现"在 prompt 里已给出**：App. E 的移动端 prompt 直接写了 INT4 "Not Supported Natively (Emulated via INT8)"（p.19），LLM 选 INT8 只是读懂了输入，而非独立发现。正文 §4.4（p.9）把这说成 agent 的硬件洞察，有夸大。
- **Table 2 的 AVG 列算不平**【核查】：按 8 个任务平均，LLaMA2-7B INT4 HAQA 应为 58.79，表中为 63.11；Human 应为 57.84，表中为 62.04；而 LLaMA3.2-3B 的 Local 行（57.51）恰好等于 8 任务平均，Human 行却是 60.57（算得 56.39）。AVG 定义不明或有错。Table 6 还把 LLaMA3-8B 写成 "LLaMA3.8-3B"（p.13）。
- **基线差异小、std 看起来过小**：HAQA 的 std 系统性地约为基线一半（Table 6），未说明重复次数/种子。LLaMA 上 HAQA 与最强基线的差距约 1–2 个点，在 10 次试验、单次 lm-eval 子集（样例中的 acc 为 0.50195…=514/1024，像是子采样评测【推断】）的噪声下不一定显著。
- 量化本身是均匀量化，"hardware-aware quantization"主要是"选整体位宽 + 调 kernel + 调微调超参"，与 HAQ 那种逐层位宽分配不是一回事。
- 每轮代价（完整微调）没报告；$5 只是 API 费用。
- 没有消融，因此**无法从本文得知动态 prompt 中哪部分信息（loss 曲线、逐任务精度、剩余轮数、ReAct）真正有用**。

## 10. 对本项目（27B 自量化 agent）的启示
- **反馈格式可借鉴**：每轮把"当前配置 JSON + 外部评测结果 + 剩余预算"追加到对话里，加上"必须在范围内、只给一组配置、首轮用默认值"这类硬约束，是一个可直接用的最小 scaffold。显式写出每个参数的类型/范围/默认值/尺度，比自然语言描述更不容易出越界配置。
- **约束校验不能只靠 prompt**：HAQA 自己报告了越界配置和格式错误。我们应在工具层做 schema 校验（bits∈{2,3,4,8}、存储预算计算），而不是指望 ReAct 文字解决。显存/存储预算计算也应由工具算，不让 LLM 心算（HAQA Table 5 依赖 LLM 心算）。
- **HAQA 证明不了诊断信号的价值**：它只给端到端精度和规格表，没有逐层信号，也没消融。我们的 profile(module,bits,quantizer)→ΔKL 工具在这个文献中没有对应物；需要自己设计消融（有/无逐层 ΔKL、有/无历史、有/无剩余预算提示）。
- **小心"prompt 泄题"**：如果给 agent 的硬件/模块描述已经暗含答案，结果就测的是阅读理解而非决策能力。评测时应区分"信息本身给出的答案"与"agent 通过工具发现的答案"。
- 历史长度管理是实际问题：27B 模型上下文有限，逐模块 profile 结果很多时，需要摘要化/表格化的历史，而不是原始日志（HAQA 直接塞原始 lm-eval 字典）。
- 预算对比：若要宣称 agent 优于搜索，需要和随机搜索/BO/贪心在**同等外部评测次数**下比较，并报告多种子方差；HAQA 在这点上不够清楚，是我们可以做得更严谨的地方。
