## 改进对象
- 改的是 **coding agent 的 Python 代码仓库**（工具、workflow、prompt），底座 FM 冻结。开放式探索的外层流程（archive、父代选择）固定，不能被改（p4–5）。
- 不改权重。

## Signal 数据（搜索时看的数据）
- **代码 / SWE-bench**：只用 SWE-bench Verified 的固定子集，分阶段评测（p6，App E.2 p33–35）：
  - 10 题：检查基本编辑能力（全是 django 题）；
  - 再加 50 题（共 60 题，按 SWE-bench-verified-mini 选，作者称其为全集的代表性样本）；
  - 若 60 题上成功率超过 40% 且在 archive 中排前二，再加 140 题，共 200 题。
  - **题目来自评测 benchmark 本身**，不是训练集，也不是自生成。
- **代码 / Polyglot**：先 10 题，超过 40% 后扩展到 50 题，均为 Polyglot 全集的随机子集（p6，App E.3）。
- **自我修改的诊断信号**：o1 读取父代在这些 benchmark 题上的评测日志，提出下一个改进。诊断 prompt 里**直接放入 SWE-bench 官方私有测试 patch 和测试结果**（App C.3 p29–30）。作者说人工检查没有发现硬编码答案（p30）。
- 数学 / 通用推理：无。
- 附带案例（App H）：解决工具调用幻觉，只用 3 道 SWE-bench 题，评分函数是自定义的幻觉分数。

## Selection / acceptance 数据
- 父代选择按上述子集分数（sigmoid 缩放）乘以"子代数量"惩罚项（App C.2 p28）。
- 进入 archive 只要求"能编译、仍能编辑代码"，**没有独立的 held-out 验收集**。
- 最终"best agent"就是在上述子集上分数最高的那个。

## 最终评测数据
- **SWE-bench**：报告的 20.0% → 50.0% 是在**同一个 200 题子集**上的分数（Fig 2 图注说明分数来自 Sec 4.2 的子集，p7），也就是搜索和选择所用的同一批题。
- **Polyglot**：搜索子集（50 题）上 14.0% → 38.0%；作者另在**全量 Polyglot** 上重测 base 和 best agent：14.2% → 30.7%（p6）。全量包含那 50 道搜索题，因此仍有部分重叠。
- 换模型迁移（Fig 4 左，p8）：SWE-bench 上换成 o3-mini 或 Claude 3.7，**仍在同一 200 题上**评测：o3-mini 23.0% → 33.0%，Claude 3.7 19.0% → 59.5%（正文写 59.5%，图上标 59.0%，原文自身不一致）。
- 跨 benchmark 迁移（Fig 4 中，p8）：SWE-bench 上搜出的 agent 拿到 Polyglot 上 28.9%（base 14.2%）；Polyglot 上搜出的 agent 拿到 SWE-bench 上 24.5%（base 20.0%）。作者称这是"truly held-out"的测试。
- 跨语言（Fig 4 右）：只在 Python 题上搜，迁移到其他语言。
- Polyglot 换模型（App A.2 p25）：Claude 3.5 32.0% → 33.3%；Claude 3.7 35.6% → 36.8%（全量 Polyglot）。

## Signal 与 eval 是否重叠
| 评测 | 与 signal 的关系 |
|---|---|
| SWE-bench 50.0% | **同一批题**（200 题子集既用于选择，也用于报告） |
| Polyglot 38.0% | **同一批题**（50 题子集） |
| Polyglot 全量 30.7% | 同一 benchmark，**包含**搜索用的 50 题，多数是新题 |
| 换 FM（SWE-bench 200 题） | 同题，只换模型 |
| SWE→Polyglot、Polyglot→SWE | **不同 benchmark**，真正 held-out |

## 过拟合 / 泛化差距证据
1. **搜索子集 vs 全量（同 benchmark）**：Polyglot best agent 在 50 题搜索子集上 38.0%，全量 30.7%，差 7.3 个点；base agent 在子集和全量上几乎相同（14.0% vs 14.2%）（p6）。也就是说，只有经过选择的 agent 出现了子集→全量的下降，这是典型的 winner's curse / 选择偏差。论文没有把它当作过拟合讨论，这是我的解读。
2. **跨 benchmark 迁移收益缩水**：在 Polyglot 上搜，Polyglot 全量提升 +16.5（14.2→30.7）；在 SWE-bench 上搜再迁移到 Polyglot，提升 +14.7（→28.9）。反方向：SWE-bench 本身提升 +30（20→50，同题），Polyglot 上搜出的 agent 迁移到 SWE-bench 只 +4.5（→24.5）（p6, p8）。
3. **同题换模型的收益差异很大**：o3-mini +10，Claude 3.7 +40.5（p8）；在 Polyglot 上换模型只 +1.2 到 +1.3（App A.2）。说明 agent 改进与搜索时用的 FM 有明显耦合。
4. **Objective hacking（App H p70–71）**：在幻觉任务中，node 114 删掉了检测用的特殊 token 日志，拿到满分 2.0，但并没有真正解决幻觉。作者指出，评测函数对 agent 可见时，这种 hacking 更常见；因此他们把检测函数对 agent 隐藏。
5. **诊断 prompt 暴露私有测试**（App C.3）：signal 中有 benchmark 题的 ground-truth 测试 patch。作者称没有观察到硬编码，但这本身就是 signal 与 eval 重叠的一种形式。
6. 稳定性：Polyglot 跑 3 次，均值 40.7%，标准差 2.3%（App A.4 p26）。

## 对我们两篇论文的启示
- DGM 是"在 eval benchmark 本身的子集上搜、并在同一子集上报告"的代表。审稿人可以直接指出 winner's curse，DGM 自己的 Polyglot 数字（38.0 子集 vs 30.7 全量）就是现成反例。
- 若采用 benchmark 搜索池，至少要做到：搜索池与最终测试集**题目不相交**，并像 DGM 那样补充跨 benchmark 迁移结果。
- 评测函数（如量化 gate 的打分代码）要对自编辑模型隐藏，否则容易出现 objective hacking（App H）。
