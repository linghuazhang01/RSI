## selection / acceptance 数据
- 选择和 evolve **用同一个集合**（式 2，p3：在同一 evolve set 上评估候选并选最优）。作者把这点明确称为"自适应复用"，引用 Dwork 等人 2015 关于 holdout 复用的工作（p3、p5）。
- RRSI 在选择侧加的正则：(1) 泄漏 critic 在评估前读 diff，拒绝编码任务名、实体名、任务特定值、答案或 benchmark 特定逻辑的修改（p5）；(2) 噪声带 δ：先多次评估未改 harness 测出噪声，候选需满足 Ŝ ≥ S★ − δ，且增益需超过 δ 才可"买"额外成本（p6）；(3) 复杂度/成本约束与剪枝。
- 超参：全部在 evolve 集上设定，**不看 held-out 或 OOD**（Table 5 注释，附录 E.1 p23）。δ 是测出来的，作者强调它不能调，否则"靠噪声就能刷 evolve 分"（p23）。

## 最终评测数据
- 代码：Terminal-Bench 2.1（evolve 集本身）+ **SWE-bench Verified（OOD）**。
- agent 工作区：Harvey LAB evolve（120）+ **Harvey LAB ID held-out（40，同 benchmark 不同 item）** + **OOD：JobBench、GDPval（185 任务）、APEX-Agents（480 任务）**。
- 工程设计：EngDesign（evolve 集本身）+ **Frontier-Eng（OOD）**；Frontier-Eng 中与 EngDesign 重复的领域被剔除（附录 B.8，p18）。

## signal 与 eval 是否重叠
- 三种关系同时出现，正好可对照：
  - **同一 items**：Terminal-Bench、EngDesign、Harvey LAB evolve 的"evolve 分"就是在搜索用过的题上测的。
  - **同 benchmark 不同 items**：Harvey LAB 120/40 固定划分。
  - **不同 benchmark**：SWE-bench Verified、JobBench、GDPval、APEX-Agents、Frontier-Eng。
- 作者主动排除跨 benchmark 的 item 重叠（Frontier-Eng 的 EngDesign 域）。

## 过拟合 / 泛化差距证据（核心）
- **Table 1（p8）Harvey LAB**：所有基线 evolve 分都涨（89.4 → 90.7–93.0），ID held-out 都差不多（88.5–89.2），**OOD 上排名翻转**：evolve 最强的 Meta-Harness OOD 平均只多 0.9；AHE、TTHE 低于起点（TTHE 低 1.7）。RRSI evolve 分最低（90.5），但 OOD 平均 43.6 vs 起点 39.7（p7）。
- **Table 2 消融（p9）**：去掉全部正则后 evolve 92.8（最高），ID held-out 88.9，OOD 平均 40.3（只比起点高 0.6），token 3.80m vs RRSI 2.42m。去掉选择侧正则：evolve 91.5、OOD 41.0。即 **evolve 分越高，OOD 越低**。
- **同 benchmark held-out 不足以发现过拟合**：ID held-out 上各方法相差很小（Table 1/2），差异只在跨 benchmark 的 OOD 上显现（p7 "separation appears out of distribution"）。
- 作者把过拟合机制分为三类：编码 benchmark 特定模式、追逐评估噪声、复杂度累积（p2）。
- 可靠性：任务级配对 bootstrap 95% CI（Table 6 p24），如 Terminal-Bench evolve +6.0 [+4.3,+9.3]，SWE-bench Verified OOD +1.8 [+1.1,+4.0]；两次独立重复最大差 1.8 点，出现在 evolve 集（Table 7 p25），作者指出 evolve 集是搜索随机性被放大的唯一地方。
- 代码域：evolve 集 Terminal-Bench 增益（Opus +6.0；Gemini Flash +14.1）远大于 OOD SWE-bench Verified 增益（+1.8；+2.2）（Table 3 p9）。

## 对我们两篇论文的启示
- 这是目前最直接的证据：**在同一 benchmark 上搜索，evolve 分与 OOD 分可以反向**；同 benchmark 的 held-out item 也几乎看不出问题。所以"benchmark 搜索池（同 benchmark 不同 item）+ 同 benchmark test"这种设计**无法证明泛化**，需要跨 benchmark 的 test。
- 可直接借鉴的 gate 设计：先测基线噪声 δ、接受门槛要求增益超过 δ；泄漏 critic 拒绝含 benchmark 特定内容的修改；所有超参只用搜索集，不看 test。
- 工具调用 / agent 工作区：Harvey LAB→JobBench/GDPval/APEX-Agents 是"搜索在一个 agent benchmark、测在其他 agent benchmark"的现成范例。
- 局限：harness 层、冻结权重，和我们改权重/LoRA 不完全一样；但"自适应复用有限搜索集"的统计问题是相同的。
