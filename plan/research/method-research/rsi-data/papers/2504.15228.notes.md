## 改进对象
- **agent 系统自身的 Python 代码库**（工具、子 agent、prompt、编排逻辑）。没有 meta-agent 和 target-agent 的区分：archive 中效用最高的 agent 来改下一代（Algorithm 1 p5）。
- 不更新权重（p3、p8）。

## Signal 数据
- **代码（主实验，p5–6）**：每代都在同一组"benchmark set"上评测：
  - SWE-bench Verified：**固定的 50 题随机子集**；
  - LiveCodeBench：**50 道随机题**；
  - 两个合成 benchmark（agent 代码库内部构造）：(1) 文件编辑，从 SWE-bench 所用仓库的相邻 commit 中挑"有意思"的编辑；(2) 代码导航，找符号定义位置。题量正文没给。
- **数学 / 推理（Sec 4.1 p7）**：另跑一组，benchmark set 是 **AIME 2024 和 GPQA Diamond**（题量未写）。
- 效用函数 U = 0.5·score + 0.25·cost 项 + 0.25·time 项（式 1 p3），超时再乘 0.5。
- meta-improvement 时 agent 读 archive，包括每代在各题上的最好、最差表现（App B p16–17），因此 signal 直接包含 benchmark 题的逐题结果。
- 自生成：只有两个合成 benchmark 是 agent 框架内"curated"的（作者说是人工 prompt 引导 agent 构造的，p8）。

## Selection / acceptance 数据
- 下一代的 meta-agent = 在**同一 benchmark set** 上效用最高的历史 agent（p3、Algorithm 1）。没有独立验证集。

## 最终评测数据
- 报告的 SWE-bench Verified 17% → 53% 就是**同一 50 题子集**上的分数（Table 1 p6；摘要 p1）。
- LCB 0.65 → 0.71（Table 1，同一 50 题）。
- AIME/GPQA：Fig 4 只画平均准确率，没有明显提升（p7）。
- **没有任何 held-out 测试**：没有换题、换 benchmark 或换模型的迁移实验。

## Signal 与 eval 是否重叠
- 所有报告数字都是**同一批题**（search = select = report）。

## 过拟合 / 泛化差距证据
1. **同一子集上分数剧烈波动**（Table 1 p6）：SWE-bV 从第 9 代 0.47 降到第 13 代 0.27，第 14 代又到 0.53。50 题子集上一次评测噪声很大，"best so far"会挑出被噪声抬高的那个，最终报告的 53% 就是这种 max。论文没有讨论置信区间对选择的影响（Fig 3 只给了均值效用的 95% CI）。这是我的推断。
2. **可能利用 benchmark 特性**：作者自己说，第 9 代的 AST 符号定位工具可能是在利用"benchmark 主要是 Python"这一点（p6，原文用了 "perhaps exploiting"）。
3. **推理任务饱和**（p7）：o3-mini 单独在 AIME / GPQA Diamond 上 87% / 79%，整个 agent 系统平均只有 76%；后加的推理组件可能打断推理模型的思维链。
4. LCB 只有微弱提升（0.65→0.71，期间最低 0.54），作者称"subtle"（p6–7）。
5. 作者承认初始提升多来自加速编辑和省钱，这部分在 SWE-bench 数字中原本体现得不多（p8）。
6. 作者预期静态 benchmark 迟早会被学完，提出自动构造 benchmark（p8）。

## 对我们两篇论文的启示
- SICA 是最"弱"的做法：搜索、选择、报告共用一个 50 题子集，没有 held-out。可以作为我们在 related work 中指出"winner's curse 未控制"的例子。
- 它的 AIME/GPQA 结果说明，在底座已强的推理任务上，scaffold 级自改进收益小；我们的权重级改动（量化或 LoRA）需要用独立测试集证明不是噪声。
